# Дневник питания

T07 реализует `/api/v1/meal-labels`, `/api/v1/diary?date=YYYY-MM-DD&zone=IANA`
и CRUD `/api/v1/diary/entries[/{entryId}]` по контракту 1.0.0. Чужой идентификатор
возвращает 404; владелец определяется только по `Actor` активной сессии.
POST требует productId, quantity, unit, occurredAt и mealLabelIds. PATCH сохраняет
отсутствующие поля, `[]` очищает лейблы; quantity и unit меняются только вместе.

Миграция 030 хранит ссылку на продукт, положительные consumed_grams, UTC-время
и связи с четырьмя стандартными пищевыми лейблами. Снимков КБЖУ, исходной единицы,
исходного количества и дневных итогов в БД нет. Удаление записи физическое,
связи удаляются каскадно, сам продукт сохраняется.

Мутации используют `CatalogTransactions.mutation` (READ COMMITTED) и общий
`CatalogMutationLock.personal`: shared base, затем exclusive owner. Проверка
`requireSelectable` выполняется отдельным statement после locks только для новой
ссылки. Прежнюю удалённую карточку разрешено сохранить при правке порции или времени.
`CatalogUnits.convert` из T12 конвертирует g/ml внутри той же транзакции; сохраняется
только результат в граммах с точностью 3 знака. Коэффициенты единиц дневник не рассчитывает.

Ответ дня строится в одном read-only REPEATABLE READ snapshot: записи,
метаданные через `CatalogRead`, актуальные КБЖУ через `CatalogCalculation.nutrition`.
Рекурсия и правила выхода принадлежат каталогу. PostgreSQL NUMERIC масштабирует
полученные значения на съеденную порцию и суммирует до округления. Лейблы читаются
отдельно от расчёта и не умножают вклад записи. Для JSON-параметра расчёта нет
ограничения количества bind-параметров на легальном дне из 10000 записей.
День с 10001-й записью отклоняется целиком. Итоги и значения порций с более чем
100 знаками целой части или 1000 знаками scale дают CALCULATION_LIMIT.

Границы дня — `[atStartOfDay(zone), nextDate.atStartOfDay(zone))`, поэтому сутки
не обязаны иметь 24 часа. Порядок: occurredAt, UUID. Ошибочная дата/неизвестный пояс
дают 422. Служебные сообщения не раскрывают SQL или содержимое дневника.

POST/PATCH материализуют актуальный ответ в той же транзакции, что и запись,
под shared base + exclusive owner locks. Ошибка расчёта порции возвращает
422 CALCULATION_LIMIT и откатывает запись вместе с пищевыми лейблами.
Перечитывается сохранённая строка, поэтому точность времени и порядок лейблов
в ответе совпадают с последующим GET. Потеря HTTP-ответа после commit всё ещё
может оставлять исход неизвестным; автоматически повторять мутацию нельзя.

Локальные проверки: `DiaryInputTest` проверяет ввод, absent/null и календарь;
`DiaryIntegrationTest` выполняет реальные HTTP/SQL проверки CRUD, прав, ретроспективных
КБЖУ, DST-границ, конвертации 200 мл × 1,03 → 206 г, лимитов, атомарного отказа
материализации и гонки новой ссылки с удалением продукта. Запуск на JDK 21 с
DB_* отдельной одноразовой PostgreSQL:

```sh
./gradlew test --tests 'ru.calorica.diary.*' integrationTest --tests 'ru.calorica.diary.*' bootJar
```

Тестовый changelog включает 001/010/020/025/030/040/050. Общий локальный прогон
T07/T09/T12 `check bootJar` на новой PostgreSQL прошёл: 20 unit и 61 integration,
включая сквозной `MvpDiaryCatalogIntegrationTest`, без ошибок и пропусков.
Локальная реализация не подтверждает выпуск на учебном стенде:
push, CI/CD и деплой запрещены текущим поручением пользователя.
