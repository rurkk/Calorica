# Правила работы с задачами Calorica

Единый порядок для разработчиков и AI-агентов, выполняющих семестровый MVP.
Первое подключение, необходимые доступы и готовый промпт —
[в инструкции нового участника](docs/team-onboarding.md).
Каждую задачу ведёт один ответственный разработчик с условным номером агента.
Он отвечает за результат целиком: тесты, реализацию, ревью, исправления,
интеграцию, релиз, отладку и ручную приёмку.

Работаем по семестровым требованиям main и источникам своей карточки.
Ветка future/product-development не используется для текущей реализации.
Расширение объёма и противоречия требований согласуются явно; агент не выбирает
удобное упрощение самостоятельно.

## 1. Выбрать задачу и проверить входы

Прочитать карточку, её критерии и источники. Проверить «Начало» в roadmap:
зависимость должна быть технически готова, а не просто кем-то взята в работу.
Для живой приёмки отдельно нужны зависимости из соответствующей колонки.
Успешная проверка на фейках не подтверждает готовность реального API.

Проверить трекер и активные брони, актуальную main, текущую ветку,
незакоммиченные изменения и origin. Общий origin должен указывать на
репозиторий команды rurkk/Calorica. Номер условного агента не резервирует задачу:
два чата одного разработчика также считаются разными исполнителями.

## 2. Забронировать до тестов и кода

Из корня репозитория проверить общие брони:

```sh
python3 scripts/roadmap/task_claim.py status
```

Пример бронирования T00 — заменить задачу, имя, чат и рабочую ветку на свои:

```sh
python3 scripts/roadmap/task_claim.py claim T00 \
  --owner 'Рауль / чат contracts-1' \
  --branch codex/t00-contracts
```

Начинать можно только после успешного ответа с claim SHA. Занятая задача,
ошибка доступа или неизвестное состояние брони запрещают самостоятельный старт.
Записать в трекере имя, чат, рабочую ветку, claim SHA и «Забронировано».
После проверки входов и фактического начала работы поставить «В работе».

При продолжении прежнего чата сверить владельца и сохранённый claim SHA через
status. Не создавать повторную бронь и не забирать чужую задачу молча.
Задача со статусом «Готово» не становится доступной заново после снятия брони.

## 3. Подготовить рабочую ветку и границы правок

Для карточки использовать отдельную ветку с префиксом codex/ от актуальной main
и изолированную рабочую копию при параллельной разработке.
Скрипт claim не создаёт рабочую ветку. codex/claims/Txx — только маркер:
его нельзя использовать для кода или вливать в main.

Менять собственную область из agents.md. Общие контракты и корневой Liquibase
changelog интегрирует агент 1, Android-навигацию и DI — агент 4,
доставку и окружение — агент 8. Владельцы предметных задач пишут свои миграции;
уже применённые changesets не переписываются.

Параллельность разрешена при выполненных зависимостях и разных зонах владения.
Изменение общего DTO, SQL-проекции или протокола блокировок согласовать
с владельцем и потребителями до реализации. Backend-деплои выполняются последовательно.
Чужие правки не отменять; конфликт интеграции не решать reset или force-push.

## 4. Выполнить Test First

1. Определить ожидаемое поведение и проверки из карточки.
2. До бизнес-кода написать unit-тесты и получить ожидаемый RED.
   Ошибка окружения или некомпилируемый тест не заменяют проверку поведения.
3. Написать реализацию, получить GREEN и выполнить рефакторинг под теми же тестами.
4. Для SQL, миграций и гонок заранее подготовить интеграционные проверки
   на отдельной PostgreSQL. Не использовать пользовательскую БД для тестов.

Отдельной стадии написания unit-тестов после кода нет. Новое поведение или найденный
дефект начинает следующий цикл: сначала воспроизводящая проверка, затем исправление.
Тесты не ослаблять ради GREEN. Серверные формулы не дублировать в Android
или тестовом расчётном движке.

Проверки выбирать по изменённому компоненту и риску. Документационные изменения
не требуют Gradle-сборки или релиза приложения. RED/GREEN и команды записывать
с точным SHA; непроверенное обозначать явно.

## 5. Вести статус и пройти ревью

Обновлять свою строку трекера при смене стадии, появлении блокера и получении
замечаний. Публиковать обновления согласованным способом: локальный файл
другим участникам не виден. Изменения чужих строк не затирать.
Бронь на origin показывает владельца ещё до попадания обновления трекера в main.

Записывать следующий шаг, фактические проверки и ссылки на ветку/изменение.
«Технически готово» означает доступный проверенный результат для потребителей,
но не заменяет ручную приёмку и статус «Готово».

Передать изменение рецензенту из карточки. В описании указать поведение,
затронутые контракты/миграции, результаты проверок и оставшиеся ограничения.
Исправить замечания, повторить затронутые проверки и интегрировать совместимую
версию. Зелёная сборка сама по себе задачу не закрывает.

## 6. Выпустить и проверить результат

Владелец задачи доводит изменённый компонент через CI/CD до опубликованной версии.
Для Android — подписанный APK с установкой/обновлением; для backend — точный
digest образа, миграции и readiness. Проверить реальный доставленный SHA
и выполнить основной сценарий на выпущенной версии.

Записать в трекере ссылки и версии APK/backend/схемы, результат собственной
отладки и короткие шаги ручной проверки. Поставить «Ожидает ручной приёмки».
Передать человеку результат для проверки; до его явного подтверждения
«Готово» не ставить. Для T00/T18 применяются исключения релизной части из workflow.

Внешние действия выполняются в рамках полученного задания и ранее выданных
разрешений. Повторно согласовывать уже разрешённое действие не требуется.
При отсутствии нужного доступа или разрешения указать конкретный блокер.
Бронь не даёт дополнительных прав на merge, релиз или изменение стенда.
Секреты и пользовательские данные не помещать в Git, промпты и отчёты;
разрушительный откат БД и изменение соседних сервисов недопустимы.

## 7. Исправить замечания и завершить задачу

Замечание ручной проверки возвращается в исходную карточку тому же владельцу:
воспроизведение на указанной версии → регрессионная проверка → исправление →
ревью → новый релиз → повторная приёмка. Межкомпонентный дефект связывается
со всеми затронутыми карточками; исправляет владелец причины.

Ошибки доступа, потеря данных, неверные КБЖУ и неработающий основной сценарий
прерывают разработку новых функций у владельца до исправления.
Неактивному агенту передать замечание и возобновить задачу: фоновая работа
сама по себе этим регламентом не запускается.

Перед «Готово» проверить:

- выполнены все критерии карточки и связанные проверки SM/SB/SN/SA;
- замечания ревью и ручной проверки устранены, нужные проверки повторены;
- зафиксированы интегрированный SHA, результаты и выпущенные версии;
- выпущенная версия отлажена, человек явно подтвердил ручную приёмку;
- итог и доказательства опубликованы в трекере.

После этого снять бронь, подставив её полный SHA:

```sh
python3 scripts/roadmap/task_claim.py release T00 --claim <полный-SHA-брони>
```

Бронь сохраняется во время ревью, релиза, исправлений и блокировки.
При передаче сначала согласовать её с владельцем, записать прогресс и блокеры,
затем снять прежнюю бронь; новый исполнитель подтверждает собственную.
Самостоятельно освобождать «давно неактивную» задачу нельзя. Зависшую бронь
разбирает координатор с записью решения в трекере.

## Краткий отчёт исполнителя

```text
Задача / разработчик / условный агент / чат:
Статус / claim SHA / рабочая ветка:
Сделано / следующий шаг / блокер:
RED и GREEN / выполненные команды / SHA:
Ревью / интеграция:
CI/CD / APK / backend digest / схема:
Проверка выпущенной версии:
Ручная приёмка: кто, версия, результат:
Дефекты и повторная проверка:
```

Подробные доказательства вести в трекере. Неизвестные результаты не выдумывать;
отсутствие реализации, устройства или доступа указывать как непроверенное.
