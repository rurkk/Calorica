# AGENTS.md

Calorica — самостоятельное Android-приложение для учёта питания, калорий и пищевых привычек. Пока репозиторий содержит продуктовую и AI-инфраструктуру; технические решения ниже — целевой контракт для начала разработки, а не описание уже существующего кода.

Обзор целевой структуры — [ARCHITECTURE.md](ARCHITECTURE.md). Перед любой UI-работой читать [docs/design-system.md](docs/design-system.md): это источник правды.

## Базовый стек после инициализации приложения

- Один Android-модуль `:app`; Compose и Material 3.
- Hilt + KSP, без kapt. Версии — только через `gradle/libs.versions.toml`.
- Room для локального источника истины; миграции только рукописные, destructive fallback запрещён.
- JUnit4; ручные фейки внутри тестовых файлов, без библиотек моков.

## Правила кода

- UI-строки остаются в Kotlin: приложение одноязычное. В ресурсы выносятся только системно необходимые значения.
- Записи о еде хранят снимок пищевой ценности на момент сохранения. Изменение карточки продукта не должно переписывать историю.
- Идентификаторы доменных сущностей стабильны и не зависят от локальной БД: это необходимо для будущей синхронизации и связывания аккаунта.
- Тяжёлые вычисления во Flow выполняются через `flowOn(@ComputeDispatcher)`, если в проекте введён этот квалификатор.
- Логирование `Log.*` не добавлять. Ошибки должны быть объяснены пользователю в UI.
- Цвета использовать только из `MaterialTheme.colorScheme`; жёстко заданные цвета разрешены лишь в `ui/theme/` и для документированных шкал данных.
- Для моушна и хаптики использовать централизованные токены проекта после их появления, а не сырые вызовы в экранах.
- Не добавлять зависимости, библиотеки графиков, анимаций или аналитики без отдельного продуктового решения.

## Данные, приватность и аналитика

- Пищевые записи, параметры профиля и вес — чувствительные пользовательские данные. Собирать и передавать только то, что необходимо явно утверждённому сценарию.
- В продуктовые события не включать названия продуктов, свободный текст, точные параметры тела или другие прямо идентифицирующие значения.
- До появления облачной синхронизации определить экспорт, удаление и жизненный цикл данных. Локальный режим остаётся полноценным.
- Продукт не даёт медицинских обещаний и не заменяет специалиста.

## Тесты и проверка

- Имена JUnit4-тестов — backtick-предложения в настоящем времени.
- Тестировать наблюдаемое поведение, а не приватные методы.
- Для ViewModel использовать `MainDispatcherRule`; для холодного `stateIn(WhileSubscribed)` прикреплять живой коллектор перед чтением состояния.
- Robolectric использовать только там, где необходим Android. Полный прогон и команды Gradle добавляются в этот документ после появления приложения.
- При UI-проверках по умолчанию использовать accessibility-дерево, UIAutomator/ADB и Compose-тесты. Не создавать и не анализировать скриншоты или видео без явной просьбы пользователя.

## Планирование и Git

- Планы и трекеры хранить в `vibe/` как `<feature>-plan.md` и `<feature>-plan-track.md`.
- Перед правками проверять текущую ветку, `git status`, последние коммиты и отличие от целевой ветки.
- Не смешивать неизвестные незакоммиченные изменения с новой задачей. Работать в тематической ветке `feat/`, `fix/`, `chore/` или `docs/`; `main` не менять напрямую.
- Коммиты писать по-русски со смысловым префиксом: `feat:`, `fix:`, `test:`, `refactor:`, `build:`, `chore:`, `docs:`.
- Не выполнять push, merge или удаление веток без явного запроса пользователя.
