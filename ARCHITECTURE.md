# Архитектура Calorica

Статус: целевой ориентир до старта Android-разработки.

## Назначение

Calorica — автономное приложение учёта питания. Оно должно работать офлайн и не требовать внешних сервисов для базовой ценности. Доменные идентификаторы и границы синхронизации проектируются устойчивыми, но внешняя интеграция не является частью текущего продукта.

## Целевой поток данных

```text
Compose screen → UI event → ViewModel → use case / repository → Room
      ↑                         │                              │
      └──── immutable UiState ←─┴──────────── Flow ────────────┘
```

- Экран отображает состояние и отправляет события; бизнес-правила не размещаются в composable.
- ViewModel владеет состоянием экрана, отменой пользовательских действий и преобразованием доменных потоков в `UiState`.
- Репозитории — единственная точка доступа к сохранённым данным и будущим удалённым источникам.
- Room — локальный источник истины. Синхронизация, когда появится, не должна обходить репозитории или заменять офлайн-сценарий.

## Домены

| Домен | Ответственность | Ключевая инварианта |
| --- | --- | --- |
| Профиль и цель | параметры, единицы, цель по калориям и БЖУ | изменение цели действует с указанной даты и не меняет прошлые итоги |
| Каталог еды | базовые и пользовательские продукты | источник и пищевая ценность различимы |
| Дневник | приёмы пищи и записи о еде | запись содержит снимок рассчитанной пищевой ценности |
| Шаблоны | избранные и повторяющиеся приёмы пищи | шаблон не меняет исторические записи |
| Вес и история | ручные измерения и агрегаты | исходные измерения сохраняются отдельно от производных трендов |
| Настройки | напоминания, формат единиц, приватность | отключённые функции не ухудшают учёт еды |

## Модель данных

- `UserProfile`, `NutritionGoal`, `FoodItem`, `MealEntry`, `MealTemplate`, `WeightEntry` — начальные сущности из [analytics-draft.md](analytics-draft.md).
- Для количества еды хранить исходную единицу, нормализованное значение и контекст порции, когда он нужен для объяснения расчёта.
- Все финансово не связанные с деньгами расчёты калорий и БЖУ должны быть детерминированными и воспроизводимыми из сохранённого снимка.
- Изменения схемы Room требуют миграции, экспортированной схемы и теста сохранности данных.

## Границы будущей синхронизации

- Публичные доменные ID создаются на устройстве и не меняются после синхронизации.
- Локальные операции должны быть идемпотентными; конфликты и удаление проектируются явно, а не как побочный эффект перезаписи.
- Транспортные DTO не проникают в UI и доменные модели.
- Учётные данные, токены и персональные сведения не хранятся в репозитории и не попадают в логи.

## Качество интерфейса

Контракты доступности, визуального языка, обратной связи и адаптивности определены в [docs/design-system.md](docs/design-system.md). Для пищевого дневника особенно важны быстрый повторный ввод, ясные единицы, возможность исправить запись и нейтральный тон.
