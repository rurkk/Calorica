# Контракт Calorica 1.0.0

Нормативный вход T02/T03/T05 и следующих задач. Машиночитаемый API —
[openapi.json](openapi.json), замороженные ответы для Android — [fixtures.json](fixtures.json).
Это целевой контракт, не объявление работающего API. Префикс всех маршрутов `/api/v1`.
HTTP health вне версии, по действующей инструкции Render. Любое несовместимое
изменение согласуется с владельцем контракта (агент 1) и потребителями до реализации;
версия документа меняется явно. Текущий SHA фиксируется в tracker.

## Общие DTO и HTTP

Все ID — UUID; ownerId=NULL означает базовый продукт. Клиент не назначает ownerId,
role, isDeleted, kind и вычисленные поля. Неизвестные поля запроса отклоняются 400.
Все decimal передаются JSON-строками с точкой, без экспоненты и знака плюс.
Сервер и Android парсят напрямую BigDecimal; Float/Double не используются.
Целые limit/dayCount/status остаются JSON-числами. Даты — YYYY-MM-DD, моменты —
ISO 8601 UTC с Z, zone — известный IANA ID. Неизвестная zone возвращает 422.
Сервер выводит kind из наличия связей; nutritionPer100g — актуальный расчёт,
manualNutrition — сохранённые ручные КБЖУ (nullable у состава).

POST создания возвращает 201 и объект, PATCH/PUT — 200 с актуальным объектом,
DELETE/logout — 204 без тела. PUT состава атомарно заменяет набор рёбер,
PATCH изменяет только переданные поля. PATCH `{}` допустим и ничего не меняет.
Absent означает «не изменять», NULL — явную очистку только nullable-поля,
`[]` — явную очистку набора. NULL вместо обязательной строки, nutrition или списка
запрещён. ProfilePatch может обнулять каждую цель; после регистрации все цели NULL.
Роль при регистрации всегда USER; Admin назначается вне публичного API.
Email trim + lower-case с уникальностью по нормализованному значению; пароль не
trim/не обрезать. 8–128 Unicode-символов, email максимум 254. Дубликат email — 409.
Технические сроки сессии и ротация — [runtime policies](../../../architecture/runtime-policies.md).
Auth rate limit: 10 register/login в минуту по IP (общий bucket), 30 refresh в минуту
по IP, 429 + Retry-After. Не логировать credentials, токены или тела питания.

Ошибки — application/problem+json, общий Problem (существующий platform/api,
расширяется T03), X-Request-Id совпадает с correlationId. Без SQL, стека и чужих ID.

| HTTP | code / применение |
| --- | --- |
| 400 | BAD_REQUEST: неверный JSON, неизвестное поле, тип, cursor |
| 401 | UNAUTHORIZED: нет/истёк/отозван токен, неверный login/refresh |
| 403 | FORBIDDEN: собственная сессия без нужной роли, запрещённый Admin cascade |
| 404 | NOT_FOUND: объект отсутствует или принадлежит другому пользователю |
| 409 | EMAIL_CONFLICT, CYCLE_DETECTED, YIELD_MODE_CONFLICT, DEPENDENCY_CONFLICT |
| 413 | REQUEST_TOO_LARGE: тело > 1 MiB |
| 422 | VALIDATION_FAILED, INVALID_COMPOSITION, PRECISION_EXCEEDED, UNIT_UNAVAILABLE, CALCULATION_LIMIT |
| 429 | TOO_MANY_REQUESTS, Retry-After в секундах |
| 503 | CALCULATION_TIMEOUT или SERVICE_UNAVAILABLE; нет частичного результата |
| 500 | INTERNAL_SERVER_ERROR, безопасное сообщение |

Вложенные ошибки имеют field (например components[0].percent) и стабильный code;
Android переводит известные коды в русские подсказки, неизвестные — общая ошибка
и correlationId. Не парсить detail как протокол.

## Состав, точность, выход

CompositionWrite принимает PERCENT либо GRAMS, не смешивает поля. Проценты >0,
<=100, до 10 знаков и в сумме ровно 100; сохранённая fraction >0, <=1, 12 знаков.
GRAMS нормализуются на сетке 10^-12 методом наибольших остатков, tie-break UUID
по возрастанию; нулевая итоговая доля — 422 PRECISION_EXCEEDED. Дубликаты productId
отклоняются. Три равные массы дают 0.333333333334 для минимального UUID и дважды
0.333333333333; Android отправляет точные 33.3333333334/33.3333333333/33.3333333333.

Для сохранённого ребра yieldFactor absent сохраняет значение, NULL очищает,
строка задаёт; для нового ребра absent означает NULL. Это позволяет Android
менять проценты без потери скрытых коэффициентов. manualYieldFactor absent
сохраняет значение, NULL очищает. При включении коэффициента хотя бы одного ребра
старый manualYieldFactor очищается атомарно; одновременный запрос ненулевого
manualYieldFactor либо outputGrams — 409 YIELD_MODE_CONFLICT.
После очистки последнего коэффициента ребра старое ручное значение не воскресает:
применяется явно переданное ручное значение или default 1.
outputGrams разрешён только GRAMS, без manualYieldFactor и заданных коэффициентов
рёбер; задаёт HALF_UP(outputGrams/sum(grams),12). Массы состава/выхода не хранятся.
PERCENT components=[] возвращает продукт к конечному: нужны сохранённые либо
переданные manualNutrition, общий выход очищается, effectiveYieldFactor=1.
Общий выход у конечного продукта задавать нельзя.

Источник выхода: INGREDIENTS при любом non-NULL k, MANUAL при заданном общем,
иначе DEFAULT. Явная 1 не равна NULL. Формулы Y, q и КБЖУ нормативно заданы в
[domain](../../domain.md); промежуточного экранного округления нет.
Общий коэффициент не меняет распределение готовых граммов до листьев.
manualNutrition и productLabelIds родителя сохраняются, игнорируются у состава.
Ручные КБЖУ без связей обязательны; переключение не делает второй тип продукта.
POST products допускает либо name+manualNutrition (конечный), либо name+composition
с непустым набором (составной, manualNutrition=NULL) атомарно. Нельзя заставлять
клиент сначала создавать лист с вымышленными нулями. T05 реализует конечный subset,
T09 добавляет создание состава, T11 — GRAMS. До реализации ветка запроса
возвращает безопасную ошибку, не создаёт частичный продукт.

## Технические лимиты

Проверять диапазон и scale ДО приведения в NUMERIC(p,s), которое иначе округляет.
Это технические предохранители; превышение отклоняет операцию целиком.

| Данные | Хранение / допустимый диапазон |
| --- | --- |
| Масса/количество | NUMERIC(10,3), 0 < x <= 9999999.999 |
| Ручные КБЖУ и цели | NUMERIC(7,2), 0 <= x <= 99999.99 |
| Доля | NUMERIC(13,12), 0 < x <= 1 |
| Заданный выход/конверсия | NUMERIC(16,12), 0 < x <= 9999.999999999999 |
| Вычисления SQL | NUMERIC без ограниченного typmod; не приводить к типу ручных КБЖУ |

Входное тело максимум 1 MiB; название trim, 1–200 символов; поиск q до 200;
до 100 разных компонентов в узле, 100 лейблов продукта, 4 пищевых лейблов.
После конверсии масса округляется HALF_UP до 3 знаков; ноль/выход за Mass — 422.
CALCULATION_LIMIT при >100000 раскрытых строк путей за один расчётный ответ,
>10000 различных узлов либо >10000 записей дневника в одном ответе/периоде.
Считать общий DAG по каждому пути; SQL UNION ALL, не DISTINCT листьев.
Не вводить произвольную глубину «один уровень». SQL statement_timeout 5 секунд,
lock_timeout 2 секунды, весь HTTP-запрос ограничен сервером 8 секундами;
Android общий таймаут 10 секунд. Прерывание => rollback и 503; никаких LIMIT,
обрезающих итог. Ограничение путей проверяется до выдачи результата, включая
(порог+1)-ю строку. Защищать от разрастания CTE и чисел: NUMERIC overflow,
вычисленный результат с >100 знаками целой части или >1000 знаками scale
возвращает CALCULATION_LIMIT без частичного ответа. Деление использует семантику
PostgreSQL NUMERIC; не обещаем бесконечную точность. Не округлять промежуточные
данные до scale 12. Выходные decimal не ограничены scale входных полей.
T09 проверяет эти предохранители на отдельной PostgreSQL, включая DAG с множеством путей.

## Поиск, доступ и удаление

GET products: базовые + свои, без удалённых; q отсутствует/пустой — весь доступный
каталог. Нормализация lower, ё→е, удаление ъ/ь, trim и схлопывание пробелов;
длина <3 — префикс, иначе exact > prefix > trigram similarity (>=0.3).
Внутри группы similarity DESC, normalizedName ASC, UUID ASC.
limit default 20, 1–100; opaque cursor до 2048 символов содержит последние ключи
порядка и fingerprint q/пользователя; несовпадение — 400. nextCursor=NULL в конце.
Каждая страница — новый снимок; при изменении каталога клиент перезагружает с начала.
Весь ответ страницы либо рассчитан, либо ошибка; карточки не пропускаются молча.

GET products/{id} позволяет владельцу читать свой удалённый продукт и доступный
базовый для истории; чужой ID — 404. Удалённый продукт нельзя вновь выбрать,
но при сохранении прежних рёбер и изменении времени/порции старой записи ссылка
остаётся допустимой. Новый productId/новое ребро всегда проверяются на доступность.
DELETE mode=KEEP_REFERENCES доступен T05; CASCADE/preview — T14 (до реализации
возвращается безопасная ошибка, не успешная имитация). Preview возвращает только
доступные affectedProductIds, cascadeAllowed=false без перечня чужих объектов.
Выполнение заново проверяет зависимости под блокировками, preview не авторизация.
Admin routes управляют базовыми объектами; не меняют личные данные.

## Дневник и серверные дополнительные операции

DiaryWrite — productId, quantity, unit g/ml, occurredAt, mealLabelIds; хранить
только consumedGrams, Instant, связи. DiaryPatch absent сохраняет поле; если меняют
quantity или unit, передать оба; если только productId — прежние граммы сохраняются,
новая ссылка проверяется. Пищевые лейблы [] очищают. NULL запрещён.
GET diary требует date и zone, возвращает весь день и total из одного снимка;
порядок occurredAt ASC, UUID ASC. Удаление записи физическое допустимо только для
своего факта питания; продукт при этом не удаляется. Повторное DELETE — 404.

Analytics period DAY/WEEK/MONTH, date внутри периода; startDate inclusive,
endDateExclusive, все days включая пустые; границы UTC получены из IANA-календаря.
Полная неделя пн–вс, месяц целиком. dailyAverage знаменатель dayCount.
mealLabels повторяют вклад записи в разные группы, total не удваивается.
productLabels распределяют готовые граммы до листьев, пересечения дают повторный
вклад по группам. Без лейбла масса не входит в группы, но остаётся в общем расчёте.

API units/лейблов/Admin/аналитики/каскада не требует новых Android-экранов в MVP.
Android редактирует состав процентами, общий выход, личные продукты и дневник в г.
Миллилитры только для базового продукта с конверсией, личные — только g.
Администратор задаёт конверсию через /admin/products/{id}/units/ml.

## Внутренние интерфейсы и Android

catalog.application — единственный публичный вход других серверных областей:
`CatalogRead.getVisible(actor, ids, includeDeletedForHistory)` возвращает Product;
`CatalogRead.requireSelectable(actor, id, tx)` проверяет доступ после блокировок.
`CatalogCalculation.nutrition(actor, productIds, snapshot)` возвращает map UUID→
NutritionPer100g/effectiveYieldFactor/yieldSource;
`CatalogCalculation.allocateLeaves(actor, portions, snapshot)` возвращает строки
(rootOrdinal, leafId, allocatedGrams) с суммой путей к одному листу в пределах порции.
portions=(rootOrdinal, productId, consumedGrams); повторы productId допустимы.
Внутренний SQL сохраняет все пути до агрегации. Лейблы присоединяются ПОСЛЕ этой
проекции; присоединение многих лейблов не удваивает КБЖУ/общую массу.
T05 реализует чтение и конечные расчёты, T09 расширяет тот же интерфейс рекурсией,
T11 добавляет режим ингредиентов. Diary и analytics не читают catalog-таблицы
для собственного расчёта и не копируют формулы на Kotlin. Snapshot — один
read-only REPEATABLE READ transaction для всех запросов ответа.

Ключи PostgreSQL advisory xact locks, 2-int namespace: base=(1128352847,0),
owner=(1128352848, hashtext(canonical UUID)). Коллизии владельцев только сериализуют.
Личная мутация графа/удаление/новая запись питания: shared base, затем exclusive
owner; базовая мутация: exclusive base. Мутации используют READ COMMITTED. Lock и последующие проверки выполняются
разными SQL statements: после ожидания advisory lock следующий statement видит
последний committed граф. Не использовать snapshot, полученный до ожидания lock,
и не распространять read-only REPEATABLE READ на write transactions.
Всё в одной транзакции, чтение после locks.
Операции не повышают shared→exclusive, не берут несколько owner; Admin cascade
при чужих зависимостях отклоняется. CatalogMutationLock принадлежит агенту 2,
T07 вызывает его, не создаёт свой порядок. После locks заново проверяются
цикл, права, isDeleted, сумма и применимость режима. Unit/label мутации,
влияющие на несколько чтений, используют тот же порядок locks и READ COMMITTED.

Android T02 определяет интерфейсы AuthRepository (register/login/refresh/logout/me),
ProductRepository (search/get/create/patch/writeComposition/delete),
DiaryRepository (day/create/patch/delete). DTO имена и поля совпадают с OpenAPI;
адаптеры обязаны сохранять absent через отдельный тип PatchField.Unchanged/Set/Clear,
не через nullable со значением по умолчанию. Decimal-проценты умножают/делят на 100
только BigDecimal, без расчёта КБЖУ. Один refresh одновременно; никаких
автоматических повторов POST/PATCH/PUT после неопределённого ответа.
Фейки используют fixtures, заменяя только явные FAKE токены, и моделируют отдельные
loading/empty/error состояния. Это не доказательство готовности живого API.

## Проверяемые сценарии потребителей

SA-07: leaves=400/80, w=.5/.5, k=.5/1.5 => Y=1, 240 ккал/100г,
порция 200 => 480, allocated=50/150. Второй k=NULL => Y=.75 и 320 ккал/100г.
SA-13: w=.6/.4, manual=.8, порция 200 => 120/80 готовых граммов.
SA-04/08: три равные массы и точный percent round-trip, 90% => 422 без записи.
SA-14: 700 в одном дне полной недели => среднее 100; два meal labels у 100 ккал
=> 100 в каждой группе и 100 total. T03 проверяет конкурирующий refresh и отзыв;
T05 — два аккаунта/базовый/удалённый/поиск; T09/T14 — конкурирующие циклы,
удаление и добавление с реальными параллельными PostgreSQL-транзакциями.

Проверка артефактов (Python 3.9+, отдельное venv):

```sh
python3 -m pip install openapi-spec-validator==0.7.2 jsonschema==4.25.1
python3 docs/semester-mvp/contracts/validate.py
git diff --check
```

Валидатор проверяет OpenAPI 3.1, уникальность operationId, типы/форматы frozen
request/response, локальные ссылки и имена миграций. Бизнес-инварианты (сумма
процентов, режим выхода, положительность) дополнительно проверяются сервером;
успешная JSON Schema сама по себе не доказывает их реализацию.
