# Как взять задачу и обозначить владельца

Общая бронь хранится на origin в ветке-маркере `codex/claims/Txx`.
Статус выполнения и доказательства — в [трекере](tracker.md).
Локальная запись в Markdown, устное назначение или номер условного агента
не заменяют общую бронь: один номер могут одновременно использовать разные чаты.

## Перед началом

Нужны Git, Python 3.9+ и право создавать ветки в репозитории.
Команды выполняются из корня Calorica. Скрипт обращается к remote с именем origin;
перед первым использованием проверить `git remote -v` и убедиться, что это общий
репозиторий команды, а не личный fork. Зависимости задачи проверяются по roadmap.

Показать все активные брони или одну задачу:

```sh
python3 scripts/roadmap/task_claim.py status
python3 scripts/roadmap/task_claim.py status T00
```

Забронировать задачу, указав человека, уникальное обозначение чата и будущую рабочую ветку:

```sh
python3 scripts/roadmap/task_claim.py claim T00 \
  --owner 'Рауль / чат contracts-1' \
  --branch codex/t00-contracts
```

Номер агента берётся из карточки задачи в main на origin.
Успех — код завершения 0 и JSON с полями owner, agent, branch, claimed_at и claim.
Поле claim — полный SHA конкретной брони, сохранить его в трекере.
Рабочая ветка при этом не создаётся; текущая ветка, index и незакоммиченные файлы
не меняются. Маркер содержит дерево опубликованной main и метаданные в сообщении
коммита, не локальные незакоммиченные файлы.

При двух одновременных заявках сервер принимает только одну.
При ненулевом коде, занятой задаче или недоступном GitHub работу не начинать.
Повторная команда не перезаписывает существующую бронь даже при том же имени:
это может быть другой чат того же разработчика. Сначала проверить status.

После подтверждения брони:

1. Обновить строку трекера: разработчик, «Забронировано», рабочая ветка и SHA брони.
2. Взять отдельную рабочую ветку/worktree от актуальной main и проверить зависимости.
3. При фактическом старте поставить «В работе», затем следовать обычному workflow.
4. Опубликовать изменение трекера обычным согласованным способом. Пока оно не попало
   в main, общая ветка-маркер уже показывает другим, что задача занята.

Короткая запись в трекере:

```text
Разработчик: Рауль
Условный агент: 1
Чат: contracts-1
Статус: В работе
Рабочая ветка: codex/t00-contracts
Бронь: <полный claim SHA>
Начало: <UTC-время claimed_at>
Следующий шаг: контракт API
```

## Пока задача выполняется

Бронь сохраняется на ревью, ожидании решения о слиянии, интеграции, релизе,
исправлениях и проверке выпущенной версии.
Не снимать её после одной отправки кода. Заблокированная задача также остаётся
за владельцем; блокер и последний прогресс записываются в трекере.
Автоматического истечения брони нет: медленная работа или закрытый чат
не означают, что задачу можно молча забрать.

Для продолжения существующей работы проверить status, сверить чат/владельца и SHA
брони, затем продолжать ту же задачу. Другой чат подключается после явного
согласования передачи или помощи с текущим владельцем.

## Завершение или передача

После явного согласия разработчика на слияние в main и успешного полного цикла
(слияние, обязательные CI/CD, нужные выпуск/деплой, проверка результата) записать
«Готово» и доказательства в трекер, опубликовать его изменение и снять свою бронь.
Второе подтверждение ручной приёмки не требуется, если разработчик отдельно его
не потребовал. При неудачной проверке или деплое задачу не закрывать. Команда:

```sh
python3 scripts/roadmap/task_claim.py release T00 --claim <полный-SHA-брони>
```

Завершённая задача не становится новой задачей только потому, что снята бронь:
перед claim всегда проверять и трекер. Дефект переоткрывает исходную карточку
у её владельца; перед новым циклом тот подтверждает новую общую бронь.

При передаче незавершённой задачи сначала согласовать её с владельцем, записать
прогресс/ветку/блокер, снять прежнюю бронь и выдать новую следующему исполнителю.
Новый исполнитель начинает только после собственного успешного claim.
Освободить зависшую бронь может координатор после выяснения состояния и записи
решения в трекере; молча удалять маркеры чужой работы нельзя.

Снятие проверяет точный SHA: устаревшая команда не удалит новую бронь той же задачи.
Если ответ release потерян, проверить status, не подставлять автоматически новый SHA.

## Как устроена защита

Скрипт использует создание удалённой Git-ссылки с условием «ссылка отсутствует»
и удаление с условием «SHA совпадает». Проверку выполняет сервер при push,
а не только клиент перед ним. Поэтому гонка двух заявок не перезаписывает владельца.
Условный параметр force-with-lease применяется только к ветке-маркеру;
история main и рабочие ветки не переписываются.

Это командный протокол координации. Участник с правами записи технически может
обойти скрипт; Git не запрещает человеку сознательно писать код без брони.
Маркер не нужно checkout, изменять, использовать для разработки или вливать в main.
CI приложения на push таких веток не запускается при текущих фильтрах main.
При ошибке чтения или неизвестном маркере задача считается недоступной для старта.

Проверки инструмента запускаются без Android/сервера:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s scripts/roadmap -p 'test_*.py'
```

Они используют отдельный локальный bare-репозиторий и две копии, не создают
брони на GitHub. Проверяются сценарии:
конкурентное бронирование, неизменность worktree, чужая/устаревшая бронь,
недоступный remote и неизвестный маркер.
