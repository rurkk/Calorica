# Правила выполнения и закрытия задач

Начало работы и единый порядок для людей и агентов — в
[CONTRIBUTING.md](../../../CONTRIBUTING.md). Здесь подробно определены проверки,
статусы и доказательства завершения.

Эти правила обязательны для каждой [карточки](README.md). Агент-владелец отвечает
за результат своей задачи целиком, включая отладку и повторные выпуски исправлений.
Передача кода другому человеку или успешная сборка сами по себе задачу не закрывают.
Commit, push рабочей ветки и PR выполняются без отдельного разрешения. После
подготовки проверенного изменения агент спрашивает разработчика:
**«Вливаем ли всё в main?»** После явного согласия самостоятельно доводит слияние,
CI/CD, нужные выпуск/деплой и проверку результата до закрытия задачи.
Дополнительная ручная приёмка нужна только по отдельному требованию разработчика.

## Бронирование перед работой

До начала работы подтвердить [общую бронь задачи](claiming.md) на origin.
Другой владелец или неизвестное состояние брони запрещают самостоятельный старт
этой задачи. Указать разработчика, уникальный чат, рабочую ветку и claim SHA
в трекере. Бронь сохраняется до завершения полного цикла либо явной передачи.
Локальная правка статуса без успешного claim не резервирует задачу.

## Реализация и проверки

Согласовать наблюдаемое поведение и проверки карточки, реализовать задачу,
добавить или обновить необходимые тесты. Порядок написания реализации и тестов
выбирается под задачу. Результат проверяется до интеграции; критерии проверок
не ослабляются ради успешного прогона.

Для SQL, транзакций, миграций и гонок нужны также интеграционные тесты на настоящем
PostgreSQL.
Unit-тесты проверяют входные данные, права, режимы и координацию сценариев;
они не заменяют исполнение рекурсивного SQL и не создают вторую реализацию формул
на Kotlin. Android проверяет состояние и преобразование ответов, не рассчитывает
авторитетные КБЖУ. Доступ к инфраструктуре покрывается проверками скриптов и
воспроизводимым прогоном; для чисто документационной задачи unit-тест не выдумывается.

Результаты фиксируются ссылкой на прогон, именами тестов и SHA. Сырые логи с секретами
или пользовательскими данными в трекер не помещаются. Существующие тесты сохраняются.

## Полный цикл

1. Проверить и подтвердить свою общую бронь, ветку, изменения, владельцев файлов,
   контракт и зависимости. При возобновлении сверить claim SHA и владельца.
2. Реализовать задачу, добавить или обновить тесты и выполнить целевые проверки.
3. Пройти ревью назначенным рецензентом; исправить замечания.
   Повторить проверки затронутых компонентов.
4. Опубликовать рабочую ветку/PR, показать разработчику изменения, результаты
   проверок и ограничения. Задать вопрос «Вливаем ли всё в main?» и поставить
   «Ожидает решения о слиянии». До явного согласия main не изменять.
   Записать ответ, дату и согласованный PR/объём; молчание не считается согласием.
5. После согласия убедиться, что обязательные проверки PR успешны, интегрировать
   версию без force-push и обхода защит и дождаться обязательных CI-проверок main.
   Проверить совместимость API и миграций с уже
   выпущенными версиями. Исправления в согласованном объёме доводить без новых
   вопросов; расширение задачи согласовывать отдельно.
6. Выпустить изменённый компонент через CI/CD: подписанный APK либо backend-образ
   по точному digest с миграциями и readiness. Проверить, что именно этот SHA
   доставлен. Документационная задача не требует релиза приложения.
7. Самостоятельно проверить выпущенную версию: для Android установка/обновление,
   основной сценарий и ошибки; для API реальные запросы, права и сохранение данных.
   Зелёный workflow без работающего сценария не считается успешным релизом.
8. Когда критерии выполнены, обязательные CI/CD и нужный деплой успешны,
   опубликовать APK/сервер/схему и доказательства, поставить «Готово» и снять
   свою бронь. После согласия на слияние второе подтверждение закрытия не нужно.
   По отдельному требованию разработчика сначала пройти указанную им приёмку.
9. При замечаниях отладить причину, исправить, повторно выпустить и повторить
   проверку. Владелец задачи остаётся прежним; инфраструктура помогает, а не
   снимает с него ответственность за доставленный результат.

Unit- и интеграционные проверки выполняются по риску и затронутому компоненту;
для Android-кода нужны тесты и сборка, для backend — его проверки с PostgreSQL
и сборка. Изменения только документов не запускают Gradle и продуктовый релиз.
Неудачные проверки, деплой и невыполненные критерии не заменяются согласием
на слияние: устранить проблему либо записать конкретный блокер. Такую задачу
не закрывать и свою бронь не снимать.

## Дефекты после ручного тестирования

Ту же задачу переоткрывают у того же условного агента. Дефект воспроизводят
на указанной версии, исправляют и подтверждают результат регрессионной проверкой.
Для дефектов устройства, сети или БД используют воспроизводимый UI- или
интеграционный сценарий. Выпускают новую версию и перепроверяют исходный сценарий.

Потеря данных, утечка доступа, неверные КБЖУ, неработающий вход или основной
сценарий прерывают развитие новых фич у владельца затронутой области до устранения.
Остальные дефекты также блокируют закрытие своей задачи. Межкомпонентный баг
связывают с обеими карточками; владелец причины исправляет свой компонент,
владельцы потребителей повторяют проверки. Нельзя «исправить» серверную формулу в Android.

Сообщение о дефекте содержит ID задачи, версию APK и backend, шаги, ожидаемый
и фактический результат, условия сети/часового пояса и безопасный correlationId.
В [трекере](tracker.md) фиксируют ответственного, причину, тест, исправляющий SHA,
новый релиз и результат повторной проверки. Неизвестные данные не выдумываются.

Это порядок реакции после получения сообщения, не обещание автоматического
фонового наблюдения. Неактивному агенту передают замечание и возобновляют задачу.
Конкретное время реакции не устанавливается без отдельного согласования.

## Зависимости и техническая готовность

Техническая готовность означает: контракт стабилен, совместимый код интегрирован,
автоматические проверки прошли и потребитель может использовать результат.
Для живого API дополнительно нужен опубликованный сервер с проверенным digest;
для APK — доступный подписанный артефакт. Это отмечается отдельно от завершения
полного цикла задачи.
T00 готовит контракты, реестр миграций и замороженные примеры для параллельной работы.

Клиент может разрабатываться на согласованных фейках до готовности API, но не
закрывается по фейкам. Начало задачи проверяется по колонке «Начало»; её приёмка —
по дополнительным зависимостям, текущему релизу и отсутствию блокирующих дефектов.
Это позволяет не создавать циклы ожидания: backend проверяется через API,
клиент проверяется с уже опубликованным backend.

## Состояния

| Состояние | Когда ставить |
| --- | --- |
| К назначению | Нет технических зависимостей; разработчик ещё не назначен |
| Ожидает зависимости | Не выполнены условия начала |
| Забронировано | Есть подтверждённая общая бронь, владелец и рабочая ветка; реализация ещё не началась |
| В работе | Назначен человек, проверены входы; идут реализация и проверки |
| Ревью | Реализация и проверки доступны рецензенту |
| Ожидает решения о слиянии | Проверенный PR показан разработчику; нужен ответ на «Вливаем ли всё в main?» |
| Ожидает интеграции | Замечания устранены; нужен общий контракт, файл или merge |
| Ожидает релиза | Интегрировано, проверки прошли; доставка ещё не подтверждена |
| Ожидает ручной приёмки | Только если разработчик отдельно потребовал такую приёмку; общий обязательный этап отменён |
| Исправление | Получен дефект; задача переоткрыта у владельца |
| Заблокировано | Нет доступа, решения или внешней зависимости; указана точная причина |
| Готово | Есть согласие на слияние, критерии выполнены, CI/CD и нужный деплой успешны, результат проверен |

Для чисто документационных T00 и координационной T18 релизная часть подтверждается
соответственно проверкой документов и ссылками на уже выпущенные компоненты.
Недоступный ключ подписи/актуальный стенд/устройство обозначает блокер, а не «Готово».

## Доказательства завершения

- Разработчик, условный агент, ветка, SHA и ссылка на ревью.
- Вопрос о слиянии, явный ответ разработчика, дата и согласованный PR/объём.
- Выполненные unit/интеграционные проверки и их результаты.
- Номера и ссылки CI/CD, APK и его версия, digest backend, версия схемы — по области задачи.
- Результат самостоятельной отладки выпущенной версии.
- Ручные шаги из карточки, проверенная версия, имя проверившего и результат.
- Все связанные дефекты закрыты или явно заблокировали задачу.

Каждый следующий релиз пересматривает затронутые доказательства. Нельзя переносить
подтверждение ручной проверки старого APK на новый без оценки и повторного прогона.
