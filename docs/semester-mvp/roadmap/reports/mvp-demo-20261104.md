# Короткая демонстрация семестрового MVP

Сценарий подготовлен по [acceptance.md](../../acceptance.md). Результат его исполнения
записывается отдельно в [матрице приёмки](mvp-acceptance-20261104.md): наличие
инструкции не означает, что шаг выполнен на релизе. Сейчас разрешена локальная
демонстрация; merge и выпуск пользователь отложил.

## Подготовка

Зафиксировать исходный SHA, APK SHA-256/versionCode/versionName/package, backend
source/digest (для локального JAR — SHA-256), восемь миграций и устройство/API.
Использовать отдельный демонстрационный аккаунт и выделенную dev-БД. Не выполнять
записи в общей Neon и не использовать чужие данные. Пароль/токены вводятся приватно
и не показываются на записи экрана, в истории shell или в отчёте.

Для воспроизведения сборки нужны JDK 21 и установленный Android SDK 37, Docker и
PostgreSQL. Справка по зависимостям и сборке: [onboarding](../../../team-onboarding.md),
[backend](../../../../backend/README.md). Инструкции инфраструктуры: [действующая доставка](../../../../deploy/render/README.md),
[безопасный persistence drill](../../../../deploy/backend/PERSISTENCE.md).
Схема исторического VPS не является текущим Render-стендом.

**Предусловие этой демонстрации — уже отдельно подготовленная QA-среда.**
Эта инструкция не воспроизводит создание локальных TLS-сертификатов, debug CA
и Gradle override. Их настраивает ответственный до демонстрации; отсутствие
такой среды блокирует запуск UI-сценария. Нельзя просто выполнить стандартный
`docker compose up` из backend README: там фиксированный project `calorica-local`
и порт 8080, которые могут принадлежать существующему стенду.

Если для подготовки используется Compose, обязательны новый уникальный project,
отдельный приватный env-файл и свободный `API_PORT`. Во всех командах указывать
`docker compose -p <unique-demo-project> --env-file <dedicated-env> -f backend/compose.yml ...`;
это требование изоляции, а не готовая команда запуска HTTPS. Отдельно проверить
настройки JWT, доступность dev-БД и TLS. Не подставлять имя/том проекта пользователя.

1. В подготовленной QA-среде сверить владельца backend/БД, выбранный свободный
   порт и отсутствие общих данных. Проверить `200 {"status":"UP"}` на readiness.
   HTTPS должен быть доверенным QA APK; production trust/TLS не отключать.
2. Установить APK, собранный для этого API. `caloricaApiBaseUrl` задаёт HTTPS origin
   и должен заканчиваться `/`; для эмулятора адрес хоста — `10.0.2.2`. Адрес API
   не устанавливает доверие сертификату. QA override 4 ноября внешен репозиторию,
   относится только к debug-сборке и не переносится в релиз.
3. Открыть приложение и создать тестовый аккаунт. Уникальный префикс продуктов
   `DEMO <дата>` позволит отличить эту демонстрацию от прошлых. Проверить, что
   выбран нужный день и системный пояс. При ошибке readiness/входа сначала
   восстановить соединение; пустой дневник не считать доказательством работы.

Ниже указаны ожидаемые значения для нового набора данных. Это контрольные числа,
не второй программный расчётный движок.

## Сценарий в Android, около 7–10 минут

| Шаг | Действие | Ожидаемый результат |
| --- | --- | --- |
| 1 | Войти; в «Продукты» найти базовую карточку и открыть её | Поиск и актуальные КБЖУ доступны; базовая карточка не редактируется пользователем |
| 2 | Создать личный `DEMO A`: на 100 г 400 ккал, Б 10, Ж 2, У 3. Создать `DEMO B`: 80 ккал, Б 10, Ж 2, У 3 | Обе карточки появляются в поиске и открываются с введёнными значениями |
| 3 | Создать `DEMO Inner` из A/B. Сначала ввести 50/40, затем исправить на 50/50. В дополнительном блоке задать общий выход 0.8 | 90% не сохраняются. При 100% состав сохраняется; выход 0.8, 300 ккал/100 г |
| 4 | Создать `DEMO Outer`, выбрать Inner как единственный компонент 100%, общий выход не задавать. В процессе выбора один раз открыть вложенный picker и вернуться | Вложенность доступна, отмена не стирает внешний черновик; Outer также 300 ккал/100 г |
| 5 | В «Дневник» добавить Outer, съеденную массу 200 г, текущее время, «завтрак» и «перекус» | Одна запись; 600 ккал, Б 25 г, Ж 5 г, У 7.5 г. Два пищевых лейбла не удваивают итог дня |
| 6 | Отредактировать массу записи до 100 г, сохранить, затем вернуть 200 г | Сначала 300 ккал, затем 600; изменяется порция, не рецептура |
| 7 | В A изменить только калории с 400 на 500. Вернуться в дневник и обновить | Старая запись Outer пересчитывается до 725 ккал; история использует текущий граф |
| 8 | Мягко удалить карточку Outer через Android, затем перечитать дневник | История и 725 ккал сохраняются; Outer недоступен для новой записи. A, B и Inner не удалены |
| 9 | Перезапустить приложение и затем выйти | Сессия до выхода восстанавливается; после выхода защищённые данные недоступны |

Если дневник уже содержит другие записи, сравнивать вклад созданной записи либо
использовать пустую тестовую дату; приведённый итог относится только к этой порции.
Для демонстрации без появления клавиатурных ошибок сохранять при открытой клавиатуре,
прокручивать до кнопки и проверить поворот экрана с незавершённой формой.

## Проверки API и сложных случаев

Эти возможности намеренно не требуют отдельных Android-экранов. На выделенной
PostgreSQL запустить реальные тесты; параметры `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`
и `AUTH_JWT_SECRET` загрузить из приватной конфигурации своей dev-среды. Не выводить
их через `env`, `echo` или debug shell. В рабочей копии кандидата выполнить:

```sh
./gradlew -p backend test integrationTest \
  --tests 'ru.calorica.catalog.CompositionIntegrationTest' \
  --tests 'ru.calorica.catalog.RecipeMassYieldIntegrationTest' \
  --tests 'ru.calorica.catalog.DeletionIntegrationTest' \
  --tests 'ru.calorica.catalog.UnitsIntegrationTest' \
  --tests 'ru.calorica.catalog.labels.ProductLabelsIntegrationTest' \
  --tests 'ru.calorica.analytics.AnalyticsIntegrationTest'
```

Для команды выше `--tests` после `integrationTest` ограничивает именно интеграционный
набор; предшествующий `test` выполняет unit-тесты. Результаты находятся в
`backend/build/reports/tests/` и `backend/build/test-results/`.

Показать фактические результаты, а при демонстрации API следовать
[замороженному OpenAPI](../../contracts/v1/openapi.json):

- 400/80 ккал, исходные 50/50, коэффициенты 0.5/1.5: Y = 1,
  240 ккал/100 г, 200 г → 480 ккал, лейблы листьев → 50/150 г.
  Android меняет название/проценты, сохраняя скрытые коэффициенты.
- Очистка второго коэффициента даёт Y = 0.75 и 320 ккал/100 г.
  Явная 1 на связи отличается от отсутствия; конфликт двух режимов отклоняется.
- GRAMS с тремя равными массами сохраняет доли с точной суммой 1.
  Процентный round-trip сохраняет `33.3333333334`, `33.3333333333`,
  `33.3333333333`; входные массы рецептуры в БД отсутствуют.
- Общий выход 0.8 и доли 60/40 распределяют готовые 200 г как 120/80 г.
  Пересекающиеся продуктовые лейблы не меняют общий итог питания.
- Неделя с 700 ккал в одном дне: семь календарных дней, среднее 100.
  Запись 100 ккал с двумя пищевыми лейблами остаётся 100 ккал в общем итоге.
- 200 мл при конверсии 1.03 → 206 г; без конверсии запрос мл отклоняется.
- Циклы, чужие ID и самоповышение роли отклоняются атомарно. Admin-preview не
  раскрывает личные зависимости. Каскад идёт к родителям и сохраняет дневник.

## Сеть и сохранность

На отдельной QA-среде проверить чтение без сети, ответ с задержкой более 10 секунд,
двойное нажатие и потерю ответа **после** server commit. Последний случай требует
контролируемого прокси/инъекции сбоя: простое отключение сети до отправки не доказывает
поведение после commit. Ожидание: конечная ошибка, один запрос, неизвестный результат
сохранения и явное перечитывание перед новой попыткой; нет автоматического replay.

Показать протокол [T17](../../../../deploy/backend/PERSISTENCE.md): реальные перезапуски
JVM и PostgreSQL, исходные и итоговые данные/ссылки, readiness при отказе БД,
отказ неудачной миграции, возврат кандидата. Нельзя демонстрировать успешный rollback
по одному health endpoint: OLD возвращает 500 при чтении новых составов.
Перспективный PR43 локально проверен как база прежних функций/данных, но ещё не выпущен.

## Фиксация результата

После выполнения записать дату, исполнителя, точные версии, пройденные шаги,
фактические контрольные числа и дефекты. Для релизной приёмки дополнительно нужны
проверки физического устройства, постоянной подписи APK, GHCR/Render digest и
доставленного SHA. Пока эти условия отсутствуют, показывать демонстрацию как
**локальный кандидат**, сохраняя ограничения из матрицы T18.
