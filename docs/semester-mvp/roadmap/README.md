# Roadmap семестрового MVP

Версия требований 1.0 · 1 ноября 2026 года; состояние сверено 7 ноября 2026.
Это рабочий список задач для разработчиков
и агентов, а не новый объём требований. Основание: [scope](../scope.md),
[домен](../domain.md), [приёмка](../acceptance.md) и
[ТЗ третьего этапа](../stage-3/technical-specification.md).
Ветка future/product-development для этих задач не используется.

Исходный учебный стенд — Render/Neon по [инструкции](../../../deploy/render/README.md).
T00 фиксирует базовый путь GitHub Actions → GHCR → Render по digest, БД Neon;
топология VPS в третьем этапе историческая. Прежний VPS сейчас недоступен.
Версионированные входы: [API/DTO](../contracts/v1/README.md),
[миграции и владельцы](../contracts/migrations.md), [аудит](../contracts/baseline.md).

## Как распределять работу

1. Прочитать [общую инструкцию для разработчиков и агентов](../../../CONTRIBUTING.md),
   выбрать карточку из таблицы ниже и проверить её зависимости и владельца.
2. Проверить трекер и [забронировать выбранную задачу на origin](claiming.md), затем записать
   разработчика, рабочую ветку и SHA брони в [трекере](tracker.md).
3. Передать выбранную карточку агенту через
   [шаблон задания](handoff-template.md). Агенты этой документацией не запускаются.
4. Только после подтверждённой брони отметить «В работе»; для задачи создать
   отдельную рабочую ветку/worktree от актуального main. Ветка-маркер — не рабочая ветка.
5. После реализации, проверок и ревью показать готовый PR разработчику и спросить
   «Вливаем ли всё в main?». После согласия выполнить слияние, обязательные CI/CD,
   необходимые выпуск/деплой, проверку результата и закрыть задачу без второго
   подтверждения приёмки. Реальные ошибки и блокеры сначала устранить.

Восемь номеров обозначают устойчивые зоны ответственности, не обязательное число
людей или одновременно работающих процессов. Один разработчик может вести несколько
агентов последовательно. Формальные роли команды для отчётов не меняются.

## Задачи и зависимости

«Начало» — минимальные технические зависимости для начала реализации.
«Живая приёмка» — дополнительные зависимости для проверки на реальном сервере
и APK. Здесь ID зависимости означает её техническую готовность по workflow,
а не обязательное завершение полного цикла всей родительской задачи.
Для всех кодовых задач выпуск также зависит от T01.

параллельно; проверка на фейках не заменяет живую приёмку.

T10 и T11 принимаются совместно после появления технически готовых APK и API:
это проверка совместимости артефактов, а не взаимное ожидание статуса «Готово».

## Что можно делать параллельно

Это окна готовности, а не календарный график. Дат, недель и бюджета трудозатрат нет.
Внутри окна задачи разных агентов выполняются параллельно при готовности своих
зависимостей. Задачи одного агента выполняются последовательно.

| Окно | Параллельные направления | Условие |
| --- | --- | --- |
| P0 | T00 / агент 1 и T01 / агент 8 | Можно назначать сразу |
| P1 | T02 / агент 4, T03 / агент 1, T05 / агент 2 | Зафиксирован T00; T01 может продолжаться |
| P2 | T04 / агент 4, T06 / агент 5, T08 / агент 6, T07 / агент 3, T09 / агент 2, T12 / агент 7 | T02 и T05 технически готовы; живые проверки ждут соответствующие API |
| P3 | T10 / агент 5, T11 / агент 2, T15 / агент 3 | Выполнены их зависимости; T12 / агент 7 может ещё продолжаться |
| P4 | T13 / агент 7 и T14 / агент 2 | T11 технически готов; T15 может ждать лейблы |
| P5 | T16 / агент 4 и T17 / агент 8 | Собраны основные клиентские и серверные функции; финальный прогон после T11–T15 |
| P6 | T18 / агент 1, исправления у владельцев соответствующих задач | Все технические зависимости доступны; проверяются принятые версии |

Параллельность не разрешает одновременно редактировать общий контракт, навигацию,
корневой changelog или публиковать несколько backend-деплоев. Владельцы общих файлов
и порядок интеграции заданы в agents.md. Ошибка в зависимости приостанавливает
связанные проверки до исправления; приёмка устаревшей версии не переносится на новую автоматически.
