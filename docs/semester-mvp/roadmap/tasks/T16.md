# T16 Сквозная отладка Android

Агент-владелец: **4**. Рецензент: **агент 6**.
Разработчик: назначается в [трекере](../tracker.md).

## Зависимости и параллельность

- Начало: T04, T06, T08, T10.
- Дополнительные условия живой приёмки: T11, T12, T13, T14, T15.
- Параллельно: P5: с T17. Исправления экранов выполняют владельцы 5/6, общую основу — агент 4.
- Требования: SM-01–SM-09; SN-05, SN-06; SA-01, SA-03–SA-05, SA-07, SA-09, SA-10, SA-15.

Все зависимости обозначают техническую готовность из [workflow](../workflow.md),
не обязательный статус «Готово». Кодовая доставка требует T01. Перед слиянием
проверенного PR агент спрашивает «Вливаем ли всё в main?». После согласия доводит
CI/CD, нужный деплой и проверки до закрытия без второго подтверждения приёмки;
недостающий доступ — блокер. Владелец не меняет чужие зоны
из [распределения ответственности](../agents.md).

## Что реализовать

- Проверить реальный сквозной сценарий вход → продукт/состав → порция → итог → правка/удаление/перезапуск.
- Проверить сеть, таймаут, потерянный ответ сохранения, повторный тап, смену аккаунта и отсутствие бесконечной загрузки.
- Проверить стандартные компоненты, русский интерфейс, 48 dp, клавиатуру и достижимость действий на API 26+, настоящем эмуляторе Android Studio. Физическое устройство заменено
  эмулятором по явному решению пользователя 7 ноября 2026; нужен подписанный APK
  и опубликованный API ([протокол](../reports/final-acceptance-20261107.md)).
- Проверить совместимость с серверными скрытыми настройками T11 и изменениями каталога; дополнительные экраны/API-возможности не включать в UI.

## Проверки

- Выполнить сквозные сценарии и unit-наборы всех клиентских компонентов.
- Исправление каждого найденного дефекта подтверждается регрессионным тестом или воспроизводимым сценарием. Проверить совместную работу результатов T02/T04/T06/T08/T10.

## Критерии приёмки

- Есть результаты на точных версиях настоящего эмулятора Android Studio и опубликованного backend.
- Каждый найденный дефект связан с исходной задачей; исправляющий релиз повторно проверен.
- Нельзя закрыть задачу с блокирующим дефектом или пометкой «проверить потом на устройстве».

## Релиз и отладка

Выпускать только исправленные компоненты. Если код не менялся, подтвердить существующие версии без фиктивного APK-релиза.

После согласия на слияние владелец проходит полный цикл из workflow, проверяет
выпущенную версию и исправляет замечания до успешного результата. Затем закрывает
задачу без второго подтверждения приёмки; одна зелёная сборка или фейки не заменяют
невыполненные критерии, нужный деплой и проверку доставленной версии.

## Ручная проверка

- Выполнить минимальную демонстрацию из acceptance.md на установленных артефактах.
- Отключить сеть во время чтения/сохранения, перезапустить процесс, сменить пояс около полуночи и сменить аккаунт.

В tracker.md заносятся результаты проверок, ревью, SHA, версии артефактов, результаты
самостоятельной проверки, согласие разработчика на слияние и итоги CI/CD/деплоя.
При дефекте эта карточка
переоткрывается у того же владельца: воспроизведение и исправление,
регрессионная проверка, нужный новый выпуск и повторная проверка результата.
