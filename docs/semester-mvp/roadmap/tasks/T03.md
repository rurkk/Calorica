# T03 Серверные аккаунты, сессии и профиль

Агент-владелец: **1**. Рецензент: **агент 2**.
Разработчик: назначается в [трекере](../tracker.md).

## Зависимости и параллельность

- Начало: T00.
- Дополнительные условия живой приёмки: T01.
- Параллельно: P1: с T02 и T05; Android auth T04 пишет клиент по зафиксированному контракту.
- Требования: SM-01; SN-01, SN-08; SA-01, SA-02; nullable-поля профиля.

Все зависимости обозначают техническую готовность из [workflow](../workflow.md),
не обязательный статус «Готово». Кодовая доставка требует T01. Перед слиянием
проверенного PR агент спрашивает «Вливаем ли всё в main?». После согласия доводит
CI/CD, нужный деплой и проверки до закрытия без второго подтверждения приёмки;
недостающий доступ — блокер. Владелец не меняет чужие зоны
из [распределения ответственности](../agents.md).

## Что реализовать

- Реализовать регистрацию email/пароль, вход, access JWT, refresh с ротацией и отзыв текущей сессии.
- Access — 15 минут, сессия — абсолютные 30 дней. Использованный refresh обнаруживается и отзывает сессию; сервер проверяет её активность и актуальные права.
- Пароли Argon2id, ограничение частоты, безопасные ошибки; пользователь не получает Admin из запроса.
- Создать профиль с необязательными ориентирами без значений при регистрации; реализовать собственные серверные операции профиля без нового обязательного Android-экрана.

## Проверки

- Unit: валидация входа, сроки, проверка прав, nullable-ориентиры, отозванная сессия и обработка повторного refresh.
- PostgreSQL: атомарная ротация, два параллельных refresh, уникальность аккаунта и изоляция профилей.

## Критерии приёмки

- Нет паролей/токенов в логах и Git; в БД хеши пароля и refresh, а не открытые значения.
- После logout access текущей сессии не принимается; чужие профиль/продукты/дневник не доступны.
- Профиль после регистрации не заполняется фиктивными целями.

## Релиз и отладка

Выпустить backend с миграциями и проверить опубликованные auth/profile endpoints; передать SHA контракта и рабочий API агенту 4 без передачи секретов.

После согласия на слияние владелец проходит полный цикл из workflow, проверяет
выпущенную версию и исправляет замечания до успешного результата. Затем закрывает
задачу без второго подтверждения приёмки; одна зелёная сборка или фейки не заменяют
невыполненные критерии, нужный деплой и проверку доставленной версии.

## Ручная проверка

- Через реальный API зарегистрировать два аккаунта, выполнить вход/refresh/выход и повторно использовать старые токены.
- Убедиться в отклонении чужого ID и самоназначения Admin; проверить профиль без ориентиров и их явное заполнение.

В tracker.md заносятся результаты проверок, ревью, SHA, версии артефактов, результаты
самостоятельной проверки, согласие разработчика на слияние и итоги CI/CD/деплоя.
При дефекте эта карточка
переоткрывается у того же владельца: воспроизведение и исправление,
регрессионная проверка, нужный новый выпуск и повторная проверка результата.
