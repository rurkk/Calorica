# T07 Серверный дневник и дневной итог

Агент-владелец: **3**. Рецензент: **агент 2**.
Разработчик: назначается в [трекере](../tracker.md).

## Зависимости и параллельность

- Начало: T05.
- Дополнительные условия живой приёмки: T03.
- Параллельно: P2: с графом T09 и единицами T12; использует публичный каталог агента 2.
- Требования: SM-06–SM-08; SB-03; SA-02, SA-09, SA-10.

Все зависимости обозначают техническую готовность из [workflow](../workflow.md),
не обязательный статус «Готово». Кодовая доставка требует T01. Перед слиянием
проверенного PR агент спрашивает «Вливаем ли всё в main?». После согласия доводит
CI/CD, нужный деплой и проверки до закрытия без второго подтверждения приёмки;
недостающий доступ — блокер. Владелец не меняет чужие зоны
из [распределения ответственности](../agents.md).

## Что реализовать

- Реализовать создание/изменение/удаление своих записей, список по выбранному локальному дню и дневной итог.
- Хранить продукт, положительные съеденные граммы, UTC-время и несколько стандартных пищевых лейблов; без КБЖУ-снапшота и единицы ввода.
- Защитить новую ссылку от гонки удаления продукта в общем порядке блокировок. Старая история сохраняется.
- Использовать общий расчёт каталога: сначала для листьев, затем без дублирования подключить рекурсивную реализацию T09. Итог не сохранять.
- Определять границы дня по IANA-поясу и диапазону [начало, конец), не считать любой день равным 24 часам.

## Проверки

- Unit: обязательность массы/времени, правила владельца, параметры диапазона, уникальность связей пищевых лейблов.
- PostgreSQL: CRUD, сумма до округления, UTC-границы, мягко удалённая карточка в истории, конкурентное создание ссылки и удаление.

## Критерии приёмки

- Правка/удаление записи обновляет итог; карточка продукта не удаляется вместе с записью.
- Изменение текущих КБЖУ влияет на перечитанный итог, несколько пищевых лейблов не удваивают его.
- Новая запись не принимает уже удалённый продукт; собственник определяется по сессии.

## Релиз и отладка

Выпустить backend; проверить дневник и итог на реальной БД и передать API агенту 6.

После согласия на слияние владелец проходит полный цикл из workflow, проверяет
выпущенную версию и исправляет замечания до успешного результата. Затем закрывает
задачу без второго подтверждения приёмки; одна зелёная сборка или фейки не заменяют
невыполненные критерии, нужный деплой и проверку доставленной версии.

## Ручная проверка

- Создать, изменить массу/продукт/дату/время/лейблы и удалить запись через реальный API.
- Изменить КБЖУ исходного продукта, перечитать историю; проверить запись около полуночи в двух поясах.

В tracker.md заносятся результаты проверок, ревью, SHA, версии артефактов, результаты
самостоятельной проверки, согласие разработчика на слияние и итоги CI/CD/деплоя.
При дефекте эта карточка
переоткрывается у того же владельца: воспроизведение и исправление,
регрессионная проверка, нужный новый выпуск и повторная проверка результата.
