# T11 Ввод масс и выход ингредиентов на сервере

Агент-владелец: **2**. Рецензент: **агент 7**.
Разработчик: назначается в [трекере](../tracker.md).

## Зависимости и параллельность

- Начало: T09.
- Дополнительные условия живой приёмки: T07, T10.
- Параллельно: P3: с клиентским T10 и аналитикой T15. T10 нужен как технически готовый APK, не как уже принятая задача.
- Требования: SB-02; SN-03; SA-07, SA-08.

Все зависимости обозначают техническую готовность из [workflow](../workflow.md),
не обязательный статус «Готово». Кодовая доставка требует T01 и выполняется
в полном цикле порученной задачи по CONTRIBUTING.md без повторных разрешений;
недостающий доступ — блокер. Владелец не меняет чужие зоны
из [распределения ответственности](../agents.md).

## Что реализовать

- Добавить ввод состава либо граммами, либо процентами; массы нормализовать в точные доли с суммой 1, распределяя остаток стабильным способом.
- Реализовать nullable-коэффициенты связей и общий выход из них, отличая NULL от явной 1; режимы не смешиваются.
- В режиме граммов вычислять ручной общий выход из необязательной готовой массы; сохранять только доли/заданные коэффициенты.
- Атомарно переключать режимы, не восстанавливать старый общий выход скрытно и не применять коэффициент связи к нутриентам повторно.
- Довести общую проекцию готовых долей листьев для T13, сохранив отдельные множители КБЖУ и граммов.

## Проверки

- Unit: выбор режима, конфликт полей, избыточная точность, нормализация равных масс и стабильный остаток.
- PostgreSQL: NULL/1, смешанные связи, вложенный выход, одинаковый общий Y при разном распределении граммов.
- Контроль: 50/50%, 400/80 ккал, выходы 0,5/1,5 дают Y=1, 240 ккал/100 г; 200 г дают 480 ккал и 50/150 г.

## Критерии приёмки

- Нет масс рецепта и сохранённого расчётного общего выхода по связям.
- Три равные массы повторно редактируются без потери точности; неверные проценты отклоняются, а не исправляются молча.
- Старый клиент не очищает скрытые настройки; скрытый дефект клиента возвращается владельцу T10.

## Релиз и отладка

Выпустить backend; совместно с технически готовым T10 проверить совместимость. Каждая задача затем получает собственное подтверждение ручной приёмки.

Владелец проходит полный цикл из workflow, проверяет выпущенную версию и исправляет
замечания ревью/ручного тестирования до повторного релиза и приёмки. Зелёная
сборка или проверка только на фейках не закрывает задачу.

## Ручная проверка

- API создать состав граммами, задать готовую массу, переключить режим и проверить структуру хранения.
- Создать разные коэффициенты связей и проверить КБЖУ порции/распределение; открыть и сохранить карточку в опубликованном APK T10.

В tracker.md заносятся результаты проверок, ревью, SHA, версии артефактов, результаты
самостоятельной проверки и явное ручное подтверждение. При дефекте эта карточка
переоткрывается у того же владельца: воспроизведение и исправление,
регрессионная проверка, новый выпуск и повторная приёмка.
