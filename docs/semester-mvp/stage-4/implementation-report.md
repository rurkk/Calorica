# Реализация и проверка MVP Calorica

Отчёт четвёртого этапа, 4 ноября 2026 года.

## 1. Результат и границы проекта

Calorica помогает вести дневник питания и видеть калории, белки, жиры и углеводы
без ручного пересчёта каждой порции. Пользователь находит или создаёт продукт,
при необходимости собирает блюдо из ингредиентов, указывает съеденную массу
и получает итог выбранного дня. Сервер хранит исходные данные, проверяет доступ
и рассчитывает пищевую ценность по текущим карточкам продуктов.

Реализован локальный кандидат семестрового MVP: Android-приложение с разделами
«Продукты» и «Дневник», серверный API и схема PostgreSQL. Исходники собраны в
[PR44](https://github.com/rurkk/Calorica/pull/44) поверх исправленного
[PR43](https://github.com/rurkk/Calorica/pull/43). Ревизия, взятая для подготовки
этого комплекта, — `9130aaa517e020e1cd43e0790de645343a57e01e`.

Отчёт сопоставляет реализацию с [ТЗ проекта](technical-specification.md)
и [планом приёмки](../acceptance.md). На эмуляторе выполнен основной сценарий
от создания продуктов до пересчёта и сохранения истории; результаты приведены
в [протоколе](test-protocol.md). Представлена локальная версия: слияние и выпуск
пользователь отложил, физическое устройство недоступно. Полная приёмка T18
остаётся открытой до выполнения этих условий и проверки доставленных артефактов.

## 2. Реализованные функции Android

Android отвечает за ввод и отображение. Состав редактируется процентами,
а масса съеденной порции задаётся отдельно в граммах. Основная навигация
содержит два раздела; формы продуктов, состава и записи дневника открываются
по действию пользователя. Использованы русский интерфейс и компоненты Compose/Material.

| Требование | Реализованное поведение |
| --- | --- |
| SM-01 — аккаунт | Регистрация по email и паролю, вход, восстановление сессии и выход. Смена аккаунта очищает состояния предыдущего пользователя |
| SM-02 — каталог | Общий список базовых и собственных продуктов, поиск, карточка с текущими КБЖУ на 100 г |
| SM-03 — личный продукт | Создание, изменение названия и ручных КБЖУ, мягкое удаление. Базовые продукты доступны для просмотра |
| SM-04 — состав | Выбор ингредиентов, включая составные продукты, редактирование процентов с точной суммой 100%, переходы между конечным и составным продуктом |
| SM-05 — выход блюда | Необязательный общий коэффициент; при серверных коэффициентах ингредиентов отображается расчётный выход, скрытые настройки сохраняются |
| SM-06 — питание | Выбор даты, продукта, положительной массы, времени и нескольких пищевых лейблов |
| SM-07 — правка питания | Изменение полей записи и её удаление без удаления продукта |
| SM-08 — итог дня | Калории и БЖУ за выбранный локальный день; обновление по текущему состоянию продуктов |
| SM-09 — состояния | Различаются загрузка, пустые данные и ошибка; доступно перечитывание, повторное сохранение блокируется на время запроса |

Особое внимание уделено сохранению пользовательского ввода. Поворот Activity
не должен уничтожать черновик, состояние выбора ингредиента или выполняемый запрос.
При возвращении в приложение учитывается текущий часовой пояс, а сохранённое
UTC-время записи остаётся неизменным. Округление предназначено для подписи на
экране: форма повторного редактирования и API используют точные значения.
Эти свойства проверялись регрессионными тестами после ревью PR43.

Для сетевой записи различаются подтверждённая ошибка и неизвестный результат.
Если сервер мог сохранить данные, но ответ потерян, приложение не сообщает
безусловный отказ и не повторяет мутацию автоматически. Пользователю предлагается
перечитать данные. Такой порядок предотвращает дублирование порции при повторном
нажатии или потере соединения. Источники: [scope](../scope.md), требования
SM-01–SM-09 и [отчёт исправлений PR43](https://github.com/rurkk/Calorica/blob/9130aaa517e020e1cd43e0790de645343a57e01e/docs/semester-mvp/roadmap/reports/pr43-review-fixes-20261104.md).

## 3. Серверные правила и API

Сервер сохраняет более широкую предметную модель, чем минимальный интерфейс.
Отдельные Android-экраны для ввода рецептуры граммами, коэффициентов ингредиентов,
миллилитров, управления продуктовыми лейблами, каскадного удаления и недельной
аналитики в семестровый объём не входят. Эти операции доступны и проверяются
через API согласно [разделению объёма](../scope.md#операции-серверного-api).

| Требование | Реализованное правило |
| --- | --- |
| SB-01 — граф продуктов | Вложенные составы без прямых и косвенных циклов; общий ингредиент учитывается по каждому пути; проверяются владелец и доступность компонентов |
| SB-02 — состав и выход | Ввод процентами или граммами, нормализация масс, общий выход либо коэффициенты связей, атомарное переключение режимов |
| SB-03 — дневник и единицы | Хранятся съеденные граммы, продукт и UTC-время; миллилитры переводятся только при наличии конверсии продукта |
| SB-04 — продуктовые лейблы | Несколько меток, распределение готовых граммов до листьев, корректная обработка пересечений и удаления связей |
| SB-05 — права и удаление | Admin управляет базовым каталогом; KEEP сохраняет связи, CASCADE направлен к зависимым родителям и повторно проверяет права |
| SB-06 — аналитика | День, календарная неделя и месяц в IANA-поясе клиента; пустые дни включаются в среднее, несколько пищевых лейблов не удваивают общий итог |

Расчёт состава использует актуальные КБЖУ компонентов, исходные массовые доли
и выход блюда. Например, два ингредиента с 400 и 80 ккал на 100 г, долями 50/50
и коэффициентами 0,5/1,5 дают выход 1 и 240 ккал на 100 г. Порция 200 г содержит
480 ккал. Коэффициент выхода не применяется второй раз к нутриентам. Отсутствие
коэффициента отличается от явно заданной единицы, поэтому API сохраняет это
различие при изменении состава.

Дневник не содержит неизменяемого снимка пищевой ценности. Правка ингредиента
меняет расчёт уже существующей записи при следующем чтении. Мягкое удаление
скрывает карточку из нового выбора, сохраняя ссылки в составах и истории.
Эти правила закреплены в [доменной модели](../domain.md) и
[OpenAPI](../contracts/v1/openapi.json); числовые примеры входят в приёмку.

## 4. Архитектура и среда проверки

Android реализован на Kotlin с Jetpack Compose, ViewModel, StateFlow и Hilt.
Репозитории обращаются к REST API через Retrofit и OkHttp; сетевые операции
выполняются корутинами вне UI-потока. Сервер на Kotlin/Spring Boot организован
как модульный монолит с компонентами accounts, catalog, diary и analytics.
Spring Security проверяет доступ, Spring JDBC выполняет явный SQL, Liquibase
управляет миграциями PostgreSQL. Android не дублирует серверный расчётный движок.

Связанные изменения выполняются в транзакциях. Для графа и удаления применяются
согласованные блокировки; ошибочная операция не должна оставить часть записи
или лейблов. Числа хранятся как NUMERIC и обрабатываются BigDecimal. Проверки
циклов, конкурентных изменений и отката используют настоящую PostgreSQL.
Это позволяет проверить свойства, которые нельзя подтвердить только фейковым API.

Действующая инфраструктура доставки описана как GitHub Actions → GHCR → Render,
а общая PostgreSQL размещена в Neon. VPS/SSH из старой презентации третьего
этапа — историческая топология, прямо отделённая в актуальном ТЗ. Сам кандидат
PR44 проверяется локально; работа прежнего общего стенда не доказывает его выпуск.
Источники: [архитектура ТЗ](../stage-3/technical-specification.md#архитектура-и-технологии),
[действующая доставка](https://github.com/rurkk/Calorica/blob/9130aaa517e020e1cd43e0790de645343a57e01e/deploy/render/README.md).

Демонстрация выполнена на эмуляторе `Calorica_PR44`, Android 16 / API 36,
с отдельным Android-пользователем и демонстрационным аккаунтом. APK имеет пакет
`com.rurkk.calorica.localpr44`; backend работает с отдельной БД через локальный
HTTPS, применены восемь миграций. Полные SHA-256 APK и JAR, исходный SHA, дата
и часовой пояс зафиксированы в [versions.json](evidence/versions.json).
Использована debug-конфигурация локального стенда. Секреты и учётные данные
в материалы не включены.

## 6. Демонстрация и реальные скриншоты

4 ноября 2026 года выполнена последовательность Android-сценариев с новым
демонстрационным аккаунтом. Регистрация открыла пустой дневник; каталог показал
базовые карточки, а поиск нашёл созданный личный продукт. Неверная сумма состава
90% и нулевая съеденная масса были отклонены с понятными сообщениями.

| Действие | Фактический результат |
| --- | --- |
| Созданы A и B с 400 и 80 ккал/100 г; Inner содержит их по 50%, общий выход 0,8 | Inner: 300 ккал, Б 12,5, Ж 2,5, У 3,75 на 100 г |
| Outer составлен из 100% Inner | Карточка Outer показывает 300 ккал/100 г; отмена выбора ингредиента сохранила имя черновика |
| Добавлена порция Outer 200 г с лейблами «завтрак» и «перекус» | Одна запись: 600 ккал, Б 25, Ж 5, У 7,5; итог не удвоился, время было предзаполнено |
| Порция изменена до 100 г, затем возвращена к 200 г и перенесена на 3 ноября, 23:50 | Итог изменился до 300 ккал; после возврата массы выбранный прошлый день показал 600 ккал |
| Калорийность A изменена с 400 до 500 ккал/100 г | Уже существующая порция Outer 200 г после обновления дала 725 ккал |
| Карточка Outer мягко удалена | Она исчезла из поиска, запись 200 г/725 ккал сохранилась; A, B и Inner остались |
| Запись дневника удалена отдельно | Выбранный день стал пустым, итог — 0; продукты сохранились |

Отключение Wi-Fi и мобильных данных показало сетевую ошибку. После восстановления
связи повторная загрузка вернула запись и 725 ккал. После принудительной остановки
и запуска приложение восстановило сессию без повторного ввода пароля. Выход
открыл форму входа; повторный вход сохранил состояние пустого дня после удаления
записи.

[Протокол](test-protocol.md) содержит шаги и доказательства; [checks.json](evidence/checks.json)
фиксирует фактические результаты с временем проверки. Реальные PNG находятся
в [screenshots](screenshots/), их происхождение — в
[ведомости снимков](evidence/screenshots.json). Данные ключевых расчётов дополнительно
проверены через API. Сведения о версии собраны в [versions.json](evidence/versions.json).

Эта демонстрация использует общий выход 0,8. Числовой пример 480 ккал из раздела 3
относится к отдельному API-сценарию с коэффициентами ингредиентов 0,5/1,5.
Результаты сложных серверных правил, таймаутов, потери ответа после commit
и перезапуска сохранены в предыдущих протоколах; свежий UI-показ повторяет
перечисленные здесь пользовательские действия.

## 8. Поставка и оставшиеся условия

Исходники, [API](../contracts/v1/openapi.json), [миграции](../contracts/migrations.md),
[инструкция backend](https://github.com/rurkk/Calorica/blob/9130aaa517e020e1cd43e0790de645343a57e01e/backend/README.md), [демонстрационный сценарий](https://github.com/rurkk/Calorica/blob/9130aaa517e020e1cd43e0790de645343a57e01e/docs/semester-mvp/roadmap/reports/mvp-demo-20261104.md)
и протоколы проверок доступны в репозитории. Локальный запуск требует отдельной
QA-конфигурации, свободных портов, изолированных данных и доверия HTTPS. Прямое
повторение Compose с именем существующего стенда не является безопасной подготовкой.

До полной приёмки необходимо выполнить основной сценарий на физическом Android;
после отдельного решения пользователя — провести merge, успешный CI/CD, выпуск
подписанного APK и backend по точному digest, проверить миграции/readiness и
доставленный SHA. До эксплуатации нужно определить совместимую опубликованную
базу возврата: текущая старая версия не читает новые составы. Затем приёмочные
результаты привязываются к финальной поставке и задачи закрываются по workflow.

Реализованный кандидат продемонстрировал основной пользовательский сценарий
с контрольными расчётами, сохранением истории и восстановлением после сетевой
ошибки. Протоколы, версии и снимки позволяют проверить этот результат.
Следующий шаг приёмки — проверка физического устройства и согласованной
опубликованной поставки.
