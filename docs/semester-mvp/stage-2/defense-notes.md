# Короткий доклад для второго этапа

Основной текст рассчитан примерно на 2–3 минуты без демонстрации приложения.
На этом этапе защищаем требования и план, не заявляем готовность реализации.

## Основной текст

Наш проект — Calorica, мобильное приложение для учёта питания с серверной частью.
Оно помогает человеку записывать съеденное и видеть калории, белки, жиры и углеводы
без ручного подсчёта.

В приложении будут два раздела: продукты и дневник.
Пользователь сможет зарегистрироваться, найти продукт в базовом каталоге или создать
свой, составить блюдо из ингредиентов и записать съеденную порцию в граммах.
В дневнике будут доступны редактирование записей и итоговые КБЖУ за выбранный день.

При этом модель продуктов сразу проектируем целевой. Блюдо может состоять из других
блюд, но не может прямо или косвенно входить в собственный состав. Сервер проверяет
эти ограничения и рассчитывает КБЖУ. Коэффициенты выхода учитывают изменение массы
при приготовлении. Некоторые дополнительные операции будут доступны только через
API и проверяться автоматическими тестами.

Мы разделили массу рецепта и массу съеденной порции. В составе хранятся доли
и коэффициенты, а в дневнике — фактически съеденные граммы. Показатели рассчитываются
по актуальным карточкам. Удаление продукта не удаляет историю питания.

Нефункциональные требования охватывают безопасность, точность расчётов, сохранность
данных, сетевые ошибки и воспроизводимый выпуск. Например, один пользователь
не должен получать чужие записи, а резервную копию нужно проверить восстановлением.

План рассчитан на два месяца и примерно двенадцать человеко-дней работы с агентами.
Восемь дней отводим основной реализации, четыре — исправлениям и подготовке к сдаче.
Сначала собираем сквозной сценарий, затем добавляем оставшиеся обязательные функции.
После этого новые возможности не вводим.

Во втором этапе мы подготовили ТЗ, границы реализации и критерии приёмки.
Результатом семестра должны стать устанавливаемое приложение, работающий сервер
и подтверждённые проверки основных сценариев и правил данных.

## Короткие ответы на вопросы

- **Как определили объём?** Выбрали сквозной сценарий учёта питания и заложили
  проверку доменных правил с учётом бюджета команды.
- **Почему это не простой CRUD?** Есть вложенный ациклический граф, выход блюда,
  рекурсивные расчёты, изоляция пользователей и ретроспективный пересчёт дневника.
- **Что доступно только через API?** Выход отдельных ингредиентов, граммы состава,
  миллилитры, продуктовые лейблы, администрирование, каскад и расширенные сводки.
- **Приложение уже готово?** Нет, сейчас предъявляем требования и план реализации.
- **Срок гарантирован?** Нет; есть резерв и ранняя проверка темпа. При отклонении
  пересматриваем план, а не убираем безопасность и правильность расчётов.
- **Что сдаём сейчас?** ТЗ семестрового MVP в DOCX/PDF; подробный план и проверки доступны
  в папке семестрового MVP.
