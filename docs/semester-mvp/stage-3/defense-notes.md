# Доклад к презентации третьего этапа Calorica

К [презентации третьего этапа](Calorica-stage-3.pdf), 8 слайдов.
Ориентировочная длительность выступления: 3–4 минуты.

## Слайд 1. Calorica

На третьем этапе мы спроектировали архитектуру Calorica — приложения для учёта
питания, калорий и БЖУ. На втором этапе определили функции и требования к качеству.
Теперь связали их с конкретными технологиями, компонентами и моделью хранения.
Объём семестровой версии остаётся прежним: продукты, составы и дневник с итогом дня.

## Слайд 2. Технологии решения

Для Android используем Kotlin и Compose, для сервера Kotlin и Spring Boot.
Сервер работает с PostgreSQL через Spring JDBC и явный SQL. Это позволяет управлять
транзакциями и рассчитывать вложенные составы рекурсивными запросами.
Схема базы развивается миграциями Liquibase. Код находится в одном репозитории,
но Android и сервер собираются и выпускаются независимо.

## Слайд 3. Архитектура приложения

Android отвечает за формы, состояние экранов и запросы. Через HTTPS он обращается
к серверу. Сервер проверяет сессию и права, выполняет операции и рассчитывает КБЖУ.
Данные хранит PostgreSQL. Бизнес-правила не дублируем на клиенте: один серверный
расчёт используют карточка продукта, дневник и календарная сводка.
После изменения клиент заново загружает актуальный результат.

## Слайд 4. Модули серверной части

Сервер представляет собой модульный монолит: одно приложение, разделённое
по предметным областям. Accounts отвечает за аккаунты и сессии, catalog — за
продукты и составы, diary — за факты питания, analytics — за сводки.
Profile хранит личные ориентиры. Внутри модулей отделяем API, сценарии, доменные
правила и SQL. Изменение состава выполняется одной транзакцией.

## Слайд 5. Модель данных

Базовые и личные продукты хранятся в одной таблице. Отдельная таблица состава
связывает блюдо с ингредиентом, его исходной долей и необязательным выходом.
Так сохраняется вложенная структура без циклов. Массы рецепта не храним.
В дневнике остаются ссылка на продукт, съеденные граммы и момент времени.
Поэтому правка карточки влияет на последующие расчёты, а мягкое удаление
не уничтожает историю питания.

## Слайд 6. Сохранение и расчёт

При сохранении сервер получает блокировку владельца и проверяет состав:
права на ингредиенты, сумму долей и отсутствие цикла. При ошибке вся операция
откатывается. При чтении рекурсивный SQL раскрывает состав до конечных продуктов.
Общий ингредиент учитывается по каждому пути. КБЖУ рассчитываем по исходным долям
и выходу блюда, а распределение готовых граммов по лейблам считаем отдельно.

## Слайд 7. Безопасность и выпуск

Сессии защищаем коротким access token и обновляемым refresh token.
Пароли хешируем, права проверяем сервером. Клиент хранит refresh token
с защитой Keystore. GitHub Actions выпускает только изменённый компонент.
Сервер разворачивается в Docker по точному digest образа, проходит миграции
и проверку готовности. Резервные копии проверяем восстановлением.

## Слайд 8. Итоги третьего этапа

Техническое задание дополнено технологиями, архитектурными схемами,
моделью данных и описанием взаимодействия компонентов. Требования второго этапа
сохранены. Для ключевых решений определены проверки: точность расчётов,
отсутствие циклов, изоляция пользователей, миграции и восстановление.
Теперь функции семестровой версии связаны с конкретными частями системы
и понятным способом проверки.
