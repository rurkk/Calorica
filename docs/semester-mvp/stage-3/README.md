shared lock ключа базового каталога для личных изменений графа, exclusive lock
для изменений базового каталога. Блокировки личных владельцев сохраняются.
Это решение описано в главе 10 и требует проверки параллельных транзакций.

## Воспроизводимость

ТЗ строится из сохранённого DOCX второго этапа с добавлением архитектурных глав.
Стили, нумерация, колонтитул и остальные неизменяемые OOXML-части сохраняются.
Старые материалы и исходные требования не перезаписываются.

[build_presentation.mjs](build_presentation.mjs) использует штатный Node runtime
и пакет @oai/artifact-tool. Переменные CALORICA_ROOT, CALORICA_ARTIFACT_WORKSPACE,
CALORICA_PRESENTATION_SKILL и CALORICA_RUNTIME_PYTHON задают пути репозитория,
временной сборки, установленного навыка презентаций и штатного Python.
RUNTIME_NODE_MODULES указывает на штатные Node-пакеты для валидатора;
CALORICA_OUTPUT_DIR позволяет выбрать новую папку для повторной сборки.
PPTX и четыре изображения схем создаются во временной папке output/.
Для запуска сборщик копируется во временный build/, где node_modules связан
с RUNTIME_NODE_MODULES. Это не требует установки пакетов в репозиторий.

Проверено 18.10.2026: 8 слайдов, 14 страниц ТЗ и 4 схемы; все страницы визуально
проверены. Текст DOCX/PDF сверён с исходниками; все 23 требования сохранены.
Это проверка материалов этапа, не протокол испытаний приложения.

[build_documents.py](build_documents.py) использует штатный Python с python-docx
и pypdf. Пример: `python -B build_documents.py --out /absolute/path/spec.docx
--assets /absolute/path/output/assets`. Затем DOCX нужно отрендерить штатным
render_docx.py с параметром --emit_pdf и проверить все страницы. Проверка текста
и сохранения шаблона: `python -B build_documents.py --out /absolute/path/spec.docx --check`.

PDF презентации экспортируется из проверенного PPTX. Настройки экспорта должны
видеть системный Helvetica Neue; подмена шрифта не допускается. После экспорта
проверяются все восемь страниц и наличие встроенных шрифтов.
