# Границы семестровой поставки

## Обязательный Android-сценарий

| ID | Возможность | Минимальная реализация |
| --- | --- | --- |
| SM-01 | Регистрация и сессия | Email/пароль, вход, восстановление сессии через refresh, выход |
| SM-02 | Каталог | Один список базовых и своих продуктов, поиск по названию, карточка с актуальными КБЖУ на 100 г |
| SM-03 | Личный конечный продукт | Создать и изменить название и ручные КБЖУ; мягко удалить с сохранением в существующих составах |
| SM-04 | Личный составной продукт | Выбрать доступные продукты, включая составные; задать проценты; сохранить, просмотреть и изменить состав |
| SM-05 | Общий выход блюда | Необязательный общий коэффициент в дополнительном блоке; по умолчанию 1; отображение эффективного выхода |
| SM-06 | Дневник | Выбрать день, по умолчанию сегодня; добавить продукт, массу съеденного в граммах, дату/время и стандартные лейблы |
| SM-07 | Правка дневника | Изменить продукт, количество, дату/время и лейблы; удалить запись; обновить данные с сервера |
| SM-08 | Дневной итог | Калории, белки, жиры, углеводы за выбранный день в виде числовой сводки над списком записей |
| SM-09 | Ошибки и загрузка | Понятные состояния загрузки, отсутствия записей и ошибки; повторная загрузка; блокировка повторного сохранения во время запроса |

Навигация: вход, затем два раздела — «Дневник» и «Продукты». Формы могут открываться
отдельными экранами. Выход доступен из меню.
Используются стандартные компоненты Compose/Material.

### Редактор состава

- В Android состав создаётся и повторно редактируется **процентами**.
  API также принимает состав граммами и преобразует массы в доли.
- Сумма ровно 100%; сервер проверяет её. В редакторе доступны точные сохранённые
  проценты без потери разрядов; краткие округлённые подписи не отправляются обратно.
- Коэффициенты отдельных ингредиентов задаются через API. Для такого состава
  карточка Android показывает источник и эффективный выход; поле общего
  коэффициента недоступно. Редактирование названия/долей не очищает скрытые настройки.
- Запросы изменения явно разделяют «поле не изменено» и «очистить значение».
  Отсутствующие в форме поля не заменяются null/пустым списком при сохранении.
- Переходы конечный ↔ составной доступны через форму состава. При возврате к конечному
  продукту нужны валидные ручные КБЖУ; если они ранее не задавались, форма запрашивает их.
- Масса съеденного обязательна в форме записи питания и вводится независимо
  от настройки карточки блюда.

## Операции серверного API

К реализации и проверке через API и доменный слой предъявляются следующие операции:

- Ввод состава граммами; расчёт выхода по готовому весу в режиме граммов.
- Выход по отдельным ингредиентам, переключение режимов и защита от двойного учёта.
- Конвертация доступных единиц г/мл, хранение результата дневника в граммах.
- Назначение продуктовых лейблов и расчёт распределённых граммов по ним.
- Администраторские операции над базовым каталогом и общими продуктовыми лейблами.
- Каскадное мягкое удаление зависимых составов с проверкой прав и предпросмотром.
- Календарная сводка КБЖУ за день/неделю/месяц и распределение по лейблам приёмов пищи.

Для проверки используется OpenAPI и воспроизводимые тесты/примеры запросов.
Сценарии SM-01—SM-09 проверяются в Android.

## Данные профиля

Необязательные личные ориентиры предусматриваются nullable-полями профиля, без
значений при регистрации.
