# План семестровой реализации

## Последовательность работ

| Работа | Проверяемый результат |
| --- | --- |
| Контракт и каркас | Схема данных, API, сессии, сервер с БД и первый запрос Android к API |
| Каталог | Базовые и личные продукты, поиск, права доступа и сквозной сценарий с конечным продуктом |
| Расчётный домен | Вложенные составы, выход, единицы и лейблы, удаление и критические серверные проверки |
| Android и интеграция | Редактор состава, дневник и дневной итог; сценарии SM-01—SM-09 |
| Проверки и выпуск | Независимый CI/CD, подписанный APK, сервер, миграции, копирование и восстановление |
| Приёмка и сдача | Исправлены блокирующие дефекты, пройдены SA-01—SA-17, подготовлены демонстрация и материалы |

Проверки ключевых правил выполняются по мере реализации. Переход к следующей
работе опирается на готовый результат и согласованный контракт. Инфраструктура
и независимые части домена могут развиваться параллельно.

## Контрольные результаты

- Первый сквозной сценарий с конечным продуктом подтверждает работу стека
  и взаимодействие клиента с сервером. При проблемах команда выясняет причину
  и корректирует последовательность работ.
- До параллельной разработки клиентов фиксируем маршруты, DTO, decimal-формат,
  ошибки, семантику PATCH и различие отсутствующего поля/NULL.
- Интегрированный кандидат должен содержать согласованные функции и позволять
  выполнить приёмочные сценарии. Перед сдачей устраняются блокирующие дефекты.
- Изменения объёма согласуются с владельцем по результатам реализации и проверок.
- Отсутствие доступа к VPS/домену/подписи блокирует соответствующую поставку,
  но не выдаётся за готовый деплой. Доступы проверяем перед работами по развёртыванию.

## Организация работы с агентами

1. Один участник координирует контракт, интеграцию и список задач; конкретное имя
   команда выбирает перед стартом. Это рабочая обязанность, не смена формальных ролей.
2. Каждой задаче задаются владелец файлов, входной контракт, критерий готовности и
   небольшой проверяемый результат. Агент не получает задачу «сделать весь MVP».
3. Независимые направления: серверный домен; Android по зафиксированному API;
   инфраструктура и приёмочные сценарии. Общие DTO/миграции имеют одного ответственного.
4. Изолированные ветки/worktree, короткие изменения, интеграция после завершения
   каждого сквозного шага. Не вести шесть расходящихся реализаций общей модели.
5. Последовательность для задачи: код → целевые проверки → ревью → исправления →
   интеграционная проверка. Для формул и безопасности контрольные примеры задаются заранее.
6. Агент сообщает, что реально запускал и что осталось непроверенным. Успешная генерация
   файлов не считается прохождением приёмки. Человек проверяет результат и границы задачи.
7. Секреты не включаются в промпты, логи и Git. Работа с общим сервером не разрешает
   менять соседние приложения или удалять их данные.

## Отчётность

Достаточно одного списка задач: ID SM/SA или доменная область, ответственный,
статус, ссылка на изменение, результат проверки и следующий блокер.
После контрольного результата команда фиксирует готовые функции, дефекты
и следующий приоритет.
