# План на два месяца и бюджет работы с агентами

## Бюджет

Шесть участников × два рабочих дня = около 12 человеко-дней суммарно.
При восьмичасовом дне — 96 часов. Это верхняя рабочая гипотеза, не подтверждённая
доступность людей. Машинное время агента не превращается автоматически в готовую функцию.

| Работа | Бюджет, человеко-дни | Результат |
| --- | --- | --- |
| Каркас сервера, контракт, сессии и первый запрос Android → API | 1 | Ранняя сквозная проверка стека и доступов |
| Целевой домен, SQL, API, миграции и критические серверные тесты | 4 | Серверные правила из domain.md и проверяемый контракт |
| Минимальный Android и интеграция с API | 2 | Сценарии SM-01—SM-09 |
| Независимый CI/CD, стенд, копирование и восстановление | 1 | Устанавливаемый APK, сервер, воспроизводимые инструкции |
| Резерв на ревью, дефекты и интеграцию | 3 | Исправлены блокирующие проблемы, пройдены обязательные проверки |
| Демонстрация, проверка комплекта и подготовка к сдаче | 1 | Воспроизводимая демонстрация и отчёт о фактическом результате |
| **Всего** | **12** | **8 на основную работу, 4 на завершение** |

Это лимиты планирования, не обещание уложить весь домен в четыре дня.
Проверки ключевых правил включены в реализацию, а не отложены до резерва.
Если оценка не подтверждается, нужна новая договорённость об объёме или времени;
нельзя незаметно заменить целевой домен упрощённым или списать проверки.

## Восемь календарных недель

| Период | Контрольная точка |
| --- | --- |
| Неделя 1 | Уточнить доступные часы, сервер/секреты и контракт; собрать сервер с БД, выполнить первый Android-запрос |
| Недели 2–3 | Получить «вход → базовый продукт → запись питания → дневной итог»; параллельно закончить целевой расчётный домен |
| Недели 4–5 | Подключить минимальный редактор состава, правку дневника, серверные API-операции; поднять автоматические выпуски |
| Неделя 6 | Заморозить функции, провести сквозную приёмку, проверить копию и восстановление |
| Неделя 7 | Только исправления, регрессия, повторная установка APK и демонстрация на чистом аккаунте |
| Неделя 8 | Финальный прогон, материалы сдачи и резерв организационных задержек |

Недельные интервалы не означают полную занятость. Два дня каждого участника лучше
разделить на несколько сессий: постановка/реализация, интеграция, исправления.
Формальные роли остаются прежними, но не ограничивают, кто может разрабатывать с агентом.

## Ранние точки остановки расширения

- После первых двух суммарных человеко-дней должен работать сквозной сценарий
  с конечным продуктом на локальном стенде. Если нет — выясняем причину и перепланируем,
  не запускаем ещё несколько независимых фич в надежде догнать срок.
- До параллельной разработки клиентов фиксируем маршруты, DTO, decimal-формат,
  ошибки, семантику PATCH и различие отсутствующего поля/NULL.
- Не позднее расходования восьми человеко-дней нужен интегрированный кандидат
  на сдачу. Если его нет, резерв используется только на обязательную поставку;
  необходимость дополнительного времени сообщается владельцу сразу.
- Резерв предназначен для исправлений и завершения приёмки. Изменения объёма
  согласуются с владельцем с учётом оставшегося бюджета.
- Отсутствие доступа к VPS/домену/подписи блокирует соответствующую поставку,
  но не выдаётся за готовый деплой. Доступы проверяем на первой неделе.

## Организация работы с агентами

1. Один участник координирует контракт, интеграцию и список задач; конкретное имя
   команда выбирает перед стартом. Это рабочая обязанность, не смена формальных ролей.
2. Каждой задаче задаются владелец файлов, входной контракт, критерий готовности и
   небольшой проверяемый результат. Агент не получает задачу «сделать весь MVP».
3. Независимые направления: серверный домен; Android по зафиксированному API;
   инфраструктура и приёмочные сценарии. Общие DTO/миграции имеют одного ответственного.
4. Изолированные ветки/worktree, короткие изменения, интеграция после завершения
   каждого сквозного шага. Не вести шесть расходящихся реализаций общей модели.
5. Последовательность для задачи: код → целевые проверки → ревью → исправления →
   интеграционная проверка. Для формул и безопасности контрольные примеры задаются заранее.
6. Агент сообщает, что реально запускал и что осталось непроверенным. Успешная генерация
   файлов не считается прохождением приёмки. Человек проверяет результат и границы задачи.
7. Секреты не включаются в промпты, логи и Git. Работа с общим сервером не разрешает
   менять соседние приложения или удалять их данные.

## Отчётность

Достаточно одного списка задач: ID SM/SA или доменная область, ответственный,
статус, затраченные часы, ссылка на изменение, результат проверки, следующий блокер.
Суммарные часы сверяются с бюджетом каждую рабочую сессию.
