# Android foundation 1.0.0 — T02

Контракт: `docs/semester-mvp/contracts/v1`, версия 1.0.0, интегрированная T00
`db7ed5f49c6de0eaf76d394869254312c604aa34`. Это общий вход для T04/T06/T08,
а не реализация регистрации, каталога, дневника или расчёта КБЖУ.

## Границы и подключение

- Агент 4: `com.rurkk.calorica.core/**`, `MainActivity`, общий manifest,
  `app/build.gradle.kts` и каталог версий. Release workflows/scripts остаются у T01.
- Агент 5: будущий `features/products/**`, экраны/состояния/адаптеры продуктов.
- Агент 6: будущий `features/diary/**`, экраны/состояния/адаптеры дневника.
- T04: будущий `features/auth/**`; восстановление сессии, Keystore и logout.
  Корневые auth/products/diary маршруты интегрируются через агента 4.

Hilt предоставляет единственные `AuthRepository`, `ProductRepository`,
`DiaryRepository`, `ConnectionRepository`, `CaloricaApi`, `OkHttpClient` и
`InMemorySession`. ViewModel внедряет интерфейс репозитория, Compose получает
состояние/обработчики. HTTP, токены и JSON не создаются внутри экранов.

`FeatureScreens` — composable slots Auth/Products/Diary/ProductPicker.
Владелец экрана передаёт свою реализацию; агент 4 подключает её в корне.
`FoundationScreens` лишь показывает подготовленные точки, без фальшивого входа,
каталога, дневных нулей или выбранного продукта. Навигационные кнопки текущей
основы доступны для проверки маршрутов; T04 подключит session gate к реальному
экрану входа. Они не означают успешную авторизацию.

Общий выбор: экран вызывает `picker.launch(ProductSelectionRequest.create(DIARY))`
либо COMPOSITION. Picker возвращает `ProductSelection(productId)` через callback.
`picker.result` приходит только вызывающему back stack entry и содержит requestId,
purpose и UUID продукта. После обработки вызвать `picker.consume()`; отмена не
создаёт результата. Навигация передаёт ID, без копии карточки/нутриентов и без
зависимости дневника от UI каталога. Выбор продукта реализуется в T06.

## Данные и запросы

Все DTO находятся в `core/api/Models.kt`, интерфейсы в `core/data/Repositories.kt`.
`ApiResult.Success` и `Failure` различаются явно. ReadController получает scope
ViewModel, предикат пустоты и suspend чтение. Перед отрисовкой используется
StateFlow/collectAsStateWithLifecycle. `close()` при уходе отменяет чтение и
сбрасывает состояние; отмена не превращается в сетевую ошибку. `Empty` сохраняет
серверный ответ (например, итог пустого дня), а ошибка никогда не создаёт пустой список.
При повторном открытии экрана выполнить новое чтение. Постоянного зеркала/очереди нет.

Decimal — BigDecimal из JSON-строки с точкой без exponent/plus. Сериализация
сохраняет decimal-строку и разряды. Только преобразование доля↔процент предусмотрено
через movePointRight/Left, без расчётов КБЖУ. Выходные значения не ограничиваются
scale входных полей; длина ограничена контрактным вычислительным пределом.
`PatchField.Unchanged/Set/Clear` сохраняет absent/value/null; Clear запрещён
для обязательных полей. Коэффициенты, отсутствующие в форме, остаются Unchanged.
ProductCreate.Composite не требует выдуманных ручных КБЖУ. DiaryPatch требует
совместного изменения quantity/unit; [] явно очищает пищевые лейблы.

Базовый адрес: HTTPS origin `https://calorica-backend.onrender.com/`.
Другой HTTPS origin задаётся `-PcaloricaApiBaseUrl=https://example.test/`.
Незащищённый HTTP, credentials, query/fragment и path prefix не допускаются в DI.
`allowHttp` у фабрики используется только из изолированных MockWebServer-тестов.
В manifest запрещён cleartext. При запуске приложение автоматически ожидает readiness
вне `/api/v1`; он не утверждает готовность бизнес-API. Отдельного раздела ручной
проверки связи в приложении нет. Fixtures не включены в APK.

Запрос ограничен общим coroutine deadline 10 секунд и OkHttp call/connect/read/write
таймаутами 10 секунд. Redirects и retryOnConnectionFailure отключены. Не повторяются
автоматически ни записи, ни чтения. Кнопка повтора чтения блокируется при загрузке.
Будущие формы должны блокировать повтор сохранения до окончания своего запроса.
При сетевом/неопределённом результате записи показывать `error.writeMessage()` и
перечитать данные перед новой попыткой, не заявлять, что запись не сохранилась.

Ошибки: известные Problem.code и field codes переводятся на русский; неизвестные
получают безопасную общую подпись. detail/HTML/стек не выводятся. UUID correlationId
можно показать для обращения; Retry-After доступен потребителю. Логирующих HTTP
interceptors нет; credentials/tokens не выводят секреты через toString.

## Сессия для T04

Access token держится только в памяти. T04 привязывает его к конкретной операции
до постановки HTTP-запроса в очередь и передаёт явным Authorization header;
interceptor не читает изменяемую сессию и удаляет header вне защищённых `/api/v1`
маршрутов настроенного origin.
Login/register/refresh и readiness не получают access token. `InMemorySession.replaceAccessToken/clear` — точки подключения.
HTTP AuthRepository возвращает Tokens, но сам не объявляет вход/выход и не хранит
refresh token. Explicit refresh сериализуется mutex, автоматического refresh нет.
T04 должен добавить single-flight orchestration: захватывать актуальный refresh
после входа в координацию, обновлять его атомарно и не отправлять заранее захваченный
старый refresh вторым caller. При неоднозначной ротации необходим повторный вход.
Keystore, восстановление, очистка пользовательских состояний и session gate — T04.

## Проверки и ручной сценарий

```sh
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ANDROID_HOME="$ANDROID_HOME" \
  ./gradlew :app:testDebugUnitTest :app:assembleDebug :app:assembleRelease :app:lintDebug
```

Unit-тесты используют непосредственно frozen fixtures T00 из test resources,
не копию контракта. MockWebServer исполняет реальные HTTP-запросы на loopback:
отсутствие ответа 10 секунд, отмена, разрыв после записи, redirects, malformed JSON,
Problem, session header и маршруты. Эти проверки не заменяют живой сервер.

На опубликованном подписанном APK:

1. Сверить release.json source SHA, версию, SHA-256 и сертификат. Установить/обновить
   APK; проверить запуск на API 26 и согласованном современном эмуляторе.
2. Открыть Дневник → Выбрать продукт → Отмена, затем Продукты, системный Назад.
   Это проверка маршрутов, продукт не выбирается фиктивно.
3. При запуске дождаться автоматической проверки готовности сервера и появления
   формы входа либо дневника. Отдельно проверить readiness API и записать адрес
   и SHA APK. UP подтверждает readiness, не auth/products/diary.
4. На отдельном тестовом устройстве отключить Wi-Fi/мобильную сеть. Повторить
   загрузку: ошибка видна, пустые данные не появляются, загрузка конечна.
   Восстановить сеть и повторить вручную. После начала запроса уйти назад: чтение отменяется.
5. Использовать ADB/UIAutomator/accessibility tree; скриншоты и видео не требуются.

Точный итог тестов, ревью, merge, релиза и устройств публикуется в tracker.md.
Ручное подтверждение человека обязательно для «Готово»; отсутствие физического
устройства или живого API указывается отдельно, а не заменяется фейком.

## Локальная реализация T04

T04 добавляет `features/auth/**` и `core/session/**` без изменения DTO и API 1.0.0.
`AuthViewModel` управляет формой и сессией; `SessionCoordinator` — единственный
владелец access/refresh. Формы требуют только email/пароль; пароль не попадает
в SavedStateHandle, rememberSaveable, файлы или toString.

`KeystoreRefreshTokenStore` хранит только AES-GCM шифротекст refresh в
`Context.noBackupFilesDir`; ключ AES находится в Android Keystore, IV случайный,
AAD привязан к package/версии формата. Backup приложения дополнительно запрещён
manifest. Access и информация о сроке доступа остаются только в памяти.

Восстановление выполняется один раз после успешного startup readiness. До отправки
refresh прежний credential удаляется с диска: гибель процесса между серверной
ротацией и сохранением ответа не приводит к повтору старого refresh при запуске.
Новые токены публикуются только после сохранения зашифрованного refresh.
Ошибка, неоднозначный результат и отмена ротации требуют повторного входа.

Защищённые ProductRepository/DiaryRepository проходят через SessionCoordinator:
перед запросом истёкший access обновляется под общим mutex; ожидающие callers
повторно проверяют текущий срок, а не отправляют заранее захваченный refresh.
Сам исходный запрос после ответа не повторяется. HTTP401 завершает соответствующую
сессию; запоздалый 401 от предыдущей версии токена не очищает новую сессию.

Перед первой точкой suspension protected operation запоминает generation сессии.
После ожидания mutex identity проверяется повторно; запрос старого аккаунта
не может получить новый token после logout/login. Immutable SessionRequestBinding
передаёт captured Authorization через coroutine context и Retrofit headers.
Задержавшийся запрос использует прежний token; OkHttp interceptor никогда не
подменяет его текущим. Mutex не удерживается во время предметного HTTP-запроса.

Session gate не позволяет открыть продукты, дневник или picker до входа.
При выходе/новом входе уничтожаются граф навигации, результаты picker и отдельный
ViewModelStore всех feature-экранов. T06/T08 сохраняют интерфейсы FeatureScreens,
ProductPickerHost, ProductRepository и DiaryRepository; их ViewModels должны жить
в текущем session/nav scope, не в singleton/Activity-поле.

Для локального режима без push/release эти изменения не означают «Готово» по
workflow: отдельно нужны успешные unit/build/lint, проверка Keystore/перезапуска
на API26 и современной версии Android и проверка выпущенного подписанного APK
с реальным backend. Точные результаты ведутся координатором в tracker.md.

## Локальная реализация T06

`features/products/**` реализует каталог и общий picker через один ProductsRoute.
ProductsViewModel создаётся фабрикой из внедрённого ProductRepository и текущего
accountId в nav/session scope. ProductsFeatureScreens подключает существующие
FeatureScreens.Products/ProductPicker; эта точечная правка MainActivity согласована
логическим владельцем agent4 в текущей локальной работе.

Поиск отменяет прежний запрос и проверяет generation перед публикацией результата;
ввод задерживается на 300 мс, серверный q ограничен 200 символами. Новая строка
сбрасывает cursor и пагинацию; ошибка следующей страницы сохраняет уже прочитанные
карточки и позволяет явно повторить GET. Пустой каталог отличается от сетевой ошибки.

Форма создаёт личный конечный продукт либо меняет name/manualNutrition собственного
конечного продукта. Decimal вводится BigDecimal, точка/запятая приводятся к строке
контракта; авторитетные КБЖУ берутся только из ответа API. ProductPatch содержит
только изменённые поля; скрытые коэффициенты, состав и лейблы не передаются как NULL.
Базовые, чужие и удалённые карточки не получают личных действий. Удаление использует
KEEP_REFERENCES с подтверждением и сохраняет существующую историю/составы.

После успешной мутации перечитываются список и карточка. Двойное нажатие не
порождает повторную запись. При неопределённом результате повторная запись
блокируется до успешного чтения: для создания выполняется поиск по названию,
для изменения/удаления читается карточка. Ошибка самого чтения не снимает блокировку.
Picker возвращает единственный ProductSelection(productId), сохраняя request/purpose
в существующем навигационном протоколе; отмена не выдаёт выбранный продукт.

Эта локальная реализация не меняет публичный контракт и не включает редактор
составов T10. Push, продуктовый релиз и живая приёмка не выполняются в локальном
режиме пользователя. Результаты unit/build/lint и устройств фиксируются отдельно.

## Интеграция T08 и замечания локального ревью

ProductsFeatureScreens.Diary подключён к DiaryRoute(diary,products,picker).
Добавление GET meal-labels и MealLabel DTO согласовано владельцем Android-основы;
справочник загружается с сервера, UUID не зашиты в экран.

До завершения GET выбранного продукта форма очищает прежний productId и блокирует
сохранение; поздний lookup отменённой формы не может изменить новую. После
неопределённой записи выбранный день фиксирован до успешного перечитывания именно
этого дня и явного подтверждения пользователем; просмотр другого дня не снимает
защиту от повторной записи.

При уходе с дневника day/labels/product GET отменяются и инвалидируются revision;
возврат запускает новые чтения. Отправленная мутация при обычном переходе на другой
экран продолжает свой единственный запрос, без повтора; если экран скрыт, перечитывание
дня откладывается до возврата. Logout уничтожает весь session ViewModelStore.
