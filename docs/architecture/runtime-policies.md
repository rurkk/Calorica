# Сессии, время, редактирование и кэш

## Авторизация: выбранные технические значения по умолчанию

Владелец поручил выбрать стандартное решение. Используем Spring Security,
короткоживущий access JWT и случайный непрозрачный refresh token.
Это собственный вход по email/паролю, не реализация OAuth password grant.

- Access token: 15 минут, передача только по HTTPS в `Authorization: Bearer`.
  Проверяются подпись, разрешённый алгоритм, issuer, audience, срок и идентификатор сессии.
- Сессия и refresh token: абсолютный срок 30 дней от входа, без бесконечного продления
  ротацией. Значения 15 минут и 30 дней — наш технический выбор, не универсальный стандарт.
- Refresh token ротируется при каждом обновлении; в БД хранятся только его хеш,
  принадлежность сессии, срок и состояние использования/отзыва. Использованные хеши
  сохраняются до истечения сессии для обнаружения повторного применения.
- Ротация атомарная. Повторное применение использованного refresh token отзывает
  соответствующую сессию. Android выполняет только одно обновление одновременно;
  при неоднозначном сетевом сбое обновления может потребоваться повторный вход.
- Выход отзывает текущую серверную сессию и удаляет локальные токены. Сервер проверяет
  активность сессии при защищённых запросах, поэтому access token также перестаёт
  приниматься после отзыва. Другие устройства автоматически не разлогиниваются.
- Права берутся из актуальных серверных данных, не из доверенного клиентского поля.
  Admin не имеет доступа к чужим личным данным.
- Пароли хешируются Argon2id с индивидуальной солью через готовую библиотеку.
  Параметры не ниже актуального минимума OWASP, проверяются на целевом сервере.
- Ограничиваем частоту регистрации, входа и refresh; не логируем пароли и токены.
- В Android access token держится в памяти; refresh token хранится зашифрованным
  ключом Android Keystore, вне резервного копирования. Это хранение сессии, не кэш питания.
- Google, восстановление и смена пароля по-прежнему вне MVP.

Основания: [OWASP — ротация refresh tokens](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html),
[OWASP — хранение паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Дата и часовой пояс

- Моменты времени хранятся как UTC: PostgreSQL `timestamptz`, Kotlin `Instant`,
  API — ISO 8601 с `Z`. Исходный часовой пояс не является частью `timestamptz`.
- Android показывает момент в текущем часовом поясе устройства и преобразует
  выбранные локальные дату/время в UTC при записи. По умолчанию используется текущий момент.
- Для дневника и аналитики клиент передаёт выбранную календарную дату и IANA zone ID
  (например, `Europe/Moscow`). Сервер определяет локальные календарные границы,
  переводит их в UTC и фильтрует диапазоном `[начало, конец)`.
- Календарная дата выбора — не UTC-момент. Нельзя превратить локальный день в день UTC
  или считать сутки всегда равными 24 часам: учитываются правила часового пояса.
- Группировка по дням выполняется сервером в том же часовом поясе. Неделя — пн–вс,
  месяц — календарный; знаменатель среднего — число календарных дней, включая пустые.
- При смене часового пояса локальное время и иногда календарный день старой записи
  меняются; запись UTC не переписывается. Аналитика использует новую локальную группировку.
- Несуществующее локальное время при переводе часов не принимается молча; для
  неоднозначного времени клиент должен определить конкретное смещение/момент.

Основание: [PostgreSQL — дата и время](https://www.postgresql.org/docs/current/datatype-datetime.html).

## Конфликты редактирования

- В MVP предполагается один Admin; пользователи не редактируют чужие продукты.
- По решению владельца не добавляем optimistic locking, версии карточек, `If-Match`
  и интерфейс разрешения конфликтов. Последнее успешно сохранённое изменение побеждает.
- Конфликты не являются технически невозможными: один аккаунт может открыть старую
  форму на другом устройстве. Риск перезаписи принимается для MVP, запрета нескольких
  устройств или сессий не вводим.
- Это не отменяет транзакции, блокировку графа по владельцу, запрет циклов, проверку
  доступа, суммы долей и валидности каждой операции.

## Минимальный кэш первой реализации

- Данные текущих экранов можно удерживать в памяти процесса; источником истины остаётся API.
- В первой реализации не строим Room-зеркало каталога/дневника, постоянный офлайн-кэш,
  фоновую синхронизацию или очередь изменений.
- После изменения обновляем затронутые данные с сервера. При повторном открытии
  экрана запрашиваем актуальные данные; хранимые в памяти значения не обещаются как актуальные.
- После завершения процесса офлайн-доступ к данным не гарантируется. Ошибка загрузки
  не подменяется пустым дневником или нулевой аналитикой.
- При выходе или смене аккаунта очищаем все пользовательские данные в памяти.
- Полноценное покрытие кэшем — отдельная задача после MVP: определить срок актуальности,
  инвалидацию, обновление зависимых расчётов и изоляцию аккаунтов. Это не разрешает
  офлайн-запись автоматически; она остаётся отдельным отложенным решением.

## Выход при вводе долями

В обоих режимах ввода состава доступны необязательные коэффициенты на связях.
Если хотя бы один задан, общий выход вычисляется по исходным долям; остальные
коэффициенты считаются равными 1. Ручной общий выход при этом недоступен.

Если все коэффициенты связей отсутствуют, можно задать общий коэффициент напрямую
либо оставить выход по умолчанию 1. В режиме граммов его также можно вычислить
по готовому весу, не сохраняя массы. Процентов и готового веса без исходной суммы
масс недостаточно; условные 100 г не подставляются. Переключение к граммам требует
нового ввода масс. Правила переключения выхода и формулы — в
[доменном документе](../requirements/domain/cooking-yield.md).
