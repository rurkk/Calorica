# Архитектура Calorica

Статус: согласованный каркас архитектуры, 28 сентября 2026 года; реализация ещё
не выполнена. Источник продуктовых правил — [требования](../requirements/README.md).
Технические значения по умолчанию, выбранные по поручению владельца, отмечены отдельно.

## Компоненты и границы

- Android: существующий Kotlin/Compose-каркас, интерфейс, состояние форм и запросы.
- Бэкенд: Kotlin + Spring Boot, модульный монолит, одно серверное приложение.
- PostgreSQL: одна база Calorica, нормализованные данные, рекурсивный SQL для расчётов.
- REST API, JSON, контракт OpenAPI. Бизнес-правила не дублируются в Android.
- Один репозиторий: Android в существующем `app/`, сервер в будущем `backend/`
  с независимой Gradle-сборкой. Документация общая, версии и выпуски независимые.
- На бэкенде один Gradle-модуль, предметные модули разделены пакетами:
  `accounts`, `profile`, `catalog`, `diary`, `analytics`.
- Внутри модуля разделены API, сценарии приложения, домен и хранение.
  Сценарии управляют правами и транзакциями; другие модули используют операции
  каталога, а не меняют его таблицы напрямую.
- Доступ к данным: Spring JDBC и явный SQL, без Hibernate/JPA.
  Расчётный SQL является общей реализацией доменных формул, не копируется в каждый
  endpoint. Kotlin координирует вызовы, проверяет входные данные и права.

## Продукты и граф

- `products`: базовые и личные продукты вместе; `owner_id IS NULL` — базовый,
  иначе указан владелец. Поля включают название, ручные КБЖУ на 100 г,
  необязательный ручной коэффициент выхода и `is_deleted`.
- `product_components`: связи `parent_product_id → child_product_id`, исходная массовая
  доля и необязательный коэффициент выхода ингредиента (`NULL` отличается от 1).
  Это рёбра графа, не отдельные карточки ингредиентов.
- При наличии коэффициента хотя бы на одной связи выход родителя вычисляется как
  `sum(share * coalesce(ingredient_yield_factor, 1))`, ручной выход отсутствует.
  Иначе используется ручной выход карточки или 1. Вычисленный выход не сохраняется.
- Наличие исходящих связей определяет составной продукт; отдельный флаг типа не нужен.
- Массы рецептуры не сохраняются. Масса съеденного хранится в записи питания.
- Лейблы и конвертации единиц — отдельные связанные таблицы.
- Базовый граф не ссылается на личные продукты; личный — только на свои и базовые.

## Расчёт при чтении

- Рекурсивный `SELECT` (`WITH RECURSIVE`) раскрывает выбранные продукты до листьев.
- Множитель КБЖУ при переходе к ребёнку: предыдущий множитель × доля / выход родителя.
  Начальный множитель равен 1; суммируются показатели листьев с этими множителями.
- Для граммов по лейблам в режиме выхода по ингредиентам используется готовая доля
  `share * coalesce(ingredient_yield_factor, 1) / parent_yield`; в общем режиме —
  исходная доля. Сумма распределённых граммов сохраняется, пересчёта в сырьё нет.
- Общий ингредиент учитывается по каждому пути: нельзя удалять вклады через `DISTINCT`.
- Мягко удалённые компоненты сохраняют участие в существующих составах и истории.
- Постоянные итоги КБЖУ, материализованная аналитика и межзапросный кэш расчётов не нужны.
- Один SQL-запрос читает согласованный снимок. Если ответ требует нескольких запросов,
  они должны читать единый снимок в read-only транзакции, например `REPEATABLE READ`.
- Защитное обнаружение цикла при чтении должно возвращать ошибку целостности,
  а не молча выдавать частичный результат. Основная проверка — при записи.
- Рекурсивное раскрытие путей не гарантирует `O(V + E)`: нагрузку проверяем отдельно
  на глубоких составах с общими компонентами. Конкретные лимиты пока не согласованы.
  [Профиль P1](../requirements/nonfunctional/performance.md) задаёт условия испытаний,
  но не жёсткие ограничения продукта.

## Конкурентные изменения

- Транзакционная advisory-блокировка по владельцу; отдельный ключ для базового каталога.
- Блокировка берётся до чтения для проверки состава и удерживается до завершения
  сохранения. Для таких изменений используем `READ COMMITTED` и читаем граф после
  получения блокировки. Все пути изменения состава соблюдают один протокол.
- Глобальной блокировки графа и блокировок отдельных узлов для проверки циклов нет.
- Состав и коэффициент сохраняются атомарно. Запрет циклов и проверка доступа обязательны.
- Защита от перезаписи устаревшей формой отдельно не реализуется, см.
  [политику редактирования](runtime-policies.md).
- Открытый технический вопрос: протокол гонок между добавлением базового ингредиента
  и его удалением, а также между каскадным удалением и созданием зависимостей.
  Блокировки разных владельцев сами по себе этот вопрос не закрывают.

## Миграции, CI/CD и размещение

- Liquibase, рукописные SQL-миграции. Применённые файлы не меняются.
- Миграции создают схему и начальные данные: около 50 продуктов, лейблы, единицы.
- CI проверяет создание БД с нуля и обновление с предыдущей версии.
- Android и сервер имеют независимые workflows проверок и выпуска. Фильтры учитывают
  код, сборочную конфигурацию и инфраструктуру соответствующего компонента.
- PR — проверки затронутых частей; `main` — после успешных проверок автоматический
  выпуск затронутых частей. Документация не запускает тяжёлые сборки и релизы.
- Android: подписанный APK и GitHub Release; публикация в Google Play не согласована.
- Сервер: Docker-образ в GHCR, деплой точного digest, миграции и проверка готовности.
- Версии независимы; теги предлагается разделить на `android-v…` и `backend-v…`.
  Повторный запуск не должен перезаписывать существующий релиз другой сборкой.
- Обязательный статус PR завершается успешно и для документационных изменений,
  без запуска Android/JVM-инструментов. Изменение workflow проверяет сам workflow,
  но не требует самостоятельного релиза приложения.
- Общий API-контракт требует проверки совместимости, не обязательного выпуска обеих частей.
- Размещение предварительно на VPS Yarumo: отдельный Compose-проект, контейнеры
  сервера и PostgreSQL, сеть, тома, секреты и резервные копии; отдельный API-поддомен
  за существующим Nginx. Ресурсы проверяются перед размещением.
- Конфигурация хоста вынесена из кода; перенос на отдельный VPS не меняет доменную логику.
- Деплои сервера последовательные. При неудаче возвращаем предыдущий совместимый
  образ, миграции БД автоматически не откатываем. Изменения схемы поэтапные и
  совместимые с предыдущим сервером; API совместим с установленными клиентами.
- Цели хранения бэкапов, RPO/RTO и проверка восстановления заданы в
  [требованиях надёжности](../requirements/nonfunctional/reliability.md).
  Адрес поддомена, ресурсы, версии зависимостей, внешнее хранилище и конкретная
  инструкция восстановления определяются перед реализацией инфраструктуры.
  Существующие workflows Calorica ещё не реализуют эту целевую схему.
