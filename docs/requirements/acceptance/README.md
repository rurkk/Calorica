# Критерии и порядок приёмки

Статус: план проверки будущего MVP. Ни один сценарий ниже не объявлен выполненным.
Приёмка ТЗ на втором этапе и приёмка реализованного приложения — разные события.

## Приёмка документации второго этапа

- Определены назначение, пользователи, семестровый объём и исключения.
- Все функциональные требования имеют ID; доменные правила доступны по ссылкам.
- NFR содержат проверяемое условие, среду/нагрузку, где это необходимо, и способ проверки.
- Числовые цели отличимы от измеренных результатов; нет обещаний ещё не выполненных работ.
- Нет противоречий в режимах выхода, составе, хранении масс, UTC, кэше и удалении.
- Подготовлен оформленный документ с титульным листом, содержанием и единым стилем;
  Markdown-пакет является исходником, но не заменяет этот пункт задания.
- После защиты материалы отправляются по указанному в задании адресу. Отправка
  выполняется отдельно по разрешению владельца, не автоматически из этого плана.

## Набор данных для функциональной проверки

Два пользователя U1/U2, один Admin, базовые и личные конечные продукты, составы
с общим ребёнком, вложенный состав, мягко удалённые компоненты, продукт с конвертацией
мл и без неё, пересекающиеся продуктовые/пищевые лейблы. Для расчётов используем
контрольные синтетические значения, не выдаваемые за пищевые справочники.

## Правила итогового решения

- Проверки выполняются на зафиксированных commit SHA, версиях клиента/сервера и миграций.
- Каждый результат отмечается как «пройден», «не пройден» или «не проверен» с доказательством.
  Отсутствие реализации или стенда — «не проверен», не автоматический успех.
- Блокирующие дефекты: потеря/раскрытие чужих данных, нарушение графа, неверный расчёт,
  невозможность основного сценария. С ними MVP не принимается.
- Для завершения приёмки обязательные AC/NFR должны пройти; отступление требует
  явного пересмотра соответствующего требования владельцем, а не скрытого исключения теста.
- Историческая доступность проверяется на доступном интервале, если пилот ещё не длится
  30 дней; месячный показатель остаётся «не проверен» до достаточного интервала.
- Формальные роли: Камила — координация проверок, Рауль и Мария — проверка соответствия
  требованиям, разработчики — устранение дефектов, Валера — эксплуатационные проверки.
  Это распределение для отчёта, не обязательная схема реальной работы команды.
