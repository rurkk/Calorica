# Надёжность, сохранность и эксплуатация

Числовые показатели ниже — цели учебного MVP. Их достижение проверяется после
развёртывания. Документ не подтверждает наличие мониторинга или резервных копий сейчас.

| ID | Требование | Проверка |
| --- | --- | --- |
| NFR-REL-01 | Запись продукта, состава и его настройки выхода атомарна; ответ об успехе отправляется после commit | Принудительная ошибка посередине операции: либо все изменения, либо ни одного |
| NFR-REL-02 | Подтверждённые записи переживают перезапуск приложения/контейнера/БД при сохранном диске; удаление продукта не удаляет историю | Перезапуск и сверка ID, количества, связей и истории; оба режима мягкого удаления |
| NFR-REL-03 | Потеря сети не выдаётся за пустой дневник или нулевую аналитику; ввод сохраняется в текущей форме, пока жив её экран; автоматической офлайн-записи нет | Отключение сети до и во время запроса; понятная ошибка и возможность повторной загрузки |
| NFR-REL-04 | При потере ответа на изменение клиент не утверждает, что операция не выполнена, и не повторяет неидемпотентную запись автоматически | Разрыв после commit: сообщение «Не удалось подтвердить сохранение», сверка после загрузки; двойное нажатие во время запроса не отправляет второй запрос |
| NFR-REL-05 | Доступность API ≥ 99% за 30 дней пилотной эксплуатации | Внешняя проверка readiness каждую минуту, включая БД; отношение успешных проверок ко всем запланированным. Деплой и пропуски мониторинга не исключаются; до 30 дней публикуется фактический интервал без заявления о месячном результате |
| NFR-REL-06 | Резервная копия БД минимум раз в 24 ч и перед миграциями; последние 7 ежедневных копий локально и 14 вне VPS | Проверка расписания, времени успешных копий, контрольных сумм и наличия внешней копии; доступ ограничен, внешняя копия зашифрована |
| NFR-REL-07 | Целевая потеря данных при аварии VPS — не более 24 ч (RPO), восстановление API — до 4 ч с момента обнаружения аварии (RTO) | Учебное восстановление внешней копии на чистом стенде: фиксируются возраст копии, начало и завершение работ, контрольные данные и readiness |
| NFR-REL-08 | Непрерывная недоступность более 5 минут или возраст последней успешной внешней копии более 24 ч вызывает уведомление ответственному | Инъекция отказов, проверка доставки; конкретный канал выбирается при настройке инфраструктуры |
| NFR-REL-09 | Деплой только проверенного digest, последовательно; ожидаемый перерыв обслуживания при штатном обновлении ≤ 5 минут | Обновление тестового стенда, пробы готовности и журнал времени; при ошибке возвращается предыдущий совместимый образ, БД автоматически не откатывается |
| NFR-REL-10 | Граф и ограничения доступа остаются корректны при конкурентных запросах, включая добавление компонента одновременно с его удалением | Транзакционные интеграционные тесты с синхронизацией запросов, не только последовательные тесты |
| NFR-OPS-01 | Миграции проверяются на пустой БД и на предыдущей версии; старый сервер совместим со схемой в окне отката | CI и тест запуска предыдущего образа после миграции; разрушительные изменения — поэтапно |
| NFR-OPS-02 | Android и сервер выпускаются независимо; документационные изменения не запускают их сборки/релизы | Проверка четырёх наборов изменений: Android, сервер, обе части, только docs; PR не имеет доступа к production-секретам |
| NFR-OPS-03 | Диагностика содержит correlation ID, тип операции, статус и длительность; нет паролей, токенов, тел запросов питания и email | Проверка логов успешных/ошибочных запросов; технические логи хранятся не более 14 дней с ограничением объёма |
| NFR-OPS-04 | Репозиторий содержит воспроизводимые инструкции запуска, миграций, деплоя, отката приложения и восстановления БД | Другой участник выполняет инструкции на чистом стенде; секреты передаются отдельно |

Резервная копия на том же диске не закрывает отказ VPS. До начала работы с реальными
данными необходимо выбрать внешнее хранилище и ответственного за уведомления;
документ не разрешает покупать сервис или менять существующий сервер автоматически.
При просрочке копии RPO считается нарушенным, а не формально выполненным расписанием.

99% — цель пилота, не договорной SLA и не высокая доступность. При использовании
общего VPS влияние соседнего приложения учитывается в реальной доступности.

Механизм копирования должен давать согласованное состояние БД и проверяемое
восстановление; возможная основа —
[pg_dump/pg_restore](https://www.postgresql.org/docs/current/backup-dump.html).
Перед восстановлением production требуется отдельное разрешение: восстановление
старой копии может потерять более новые данные. При приёмке используем изолированный стенд.
