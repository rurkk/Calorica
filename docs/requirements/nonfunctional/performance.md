# Производительность и нагрузка

## Проверочный профиль P1

Это проектный профиль приёмки, не установленный запрет на больший объём данных.
Стартовые около 50 продуктов не заменяют нагрузочный набор.

- 100 зарегистрированных пользователей, 10 одновременно активных сессий.
- 5 000 базовых продуктов, по 500 личных продуктов и 3 000 записей питания на аккаунт.
  Всего 55 000 продуктов и 300 000 записей; данные синтетические, не персональные.
- 20% продуктов составные; максимальная глубина проверочного графа — 8 связей,
  до 20 прямых ингредиентов, до 300 разных достижимых узлов и до 5 000 путей к листьям
  на проверяемый корень. Эти границы выполняются одновременно. Есть общие ингредиенты
  по нескольким путям, мягко удалённые компоненты, оба режима выхода и лейблы с пересечениями.
- В выбранном для месячной аналитики месяце — 300 записей на тестируемый аккаунт.
- Эталонный стенд: суммарно для Calorica 2 vCPU, 4 ГиБ RAM, SSD; без конкурирующей
  нагрузки других приложений. На общем VPS ресурсы необходимо подтвердить отдельно;
  неизвестные характеристики текущего хоста не считаются соответствующими автоматически.
- Измерение API на входе HTTPS со стороны нагрузочного клиента, RTT до сервера ≤ 50 мс.
  Время включает авторизацию, SQL и сериализацию, но не рендер Android.
- 2 минуты прогрева и 15 минут измерения с открытой интенсивностью 5 запросов/с,
  распределённых между 10 сессиями: поиск 35%, карточка 20%, дневник 15%, аналитика 15%,
  запись питания 10%, сохранение состава 5%. На каждую группу — минимум 100 измерений.
  Неотправленные из-за перегрузки запросы учитываются как сбой, а не пропускаются.
- Результат: версия кода, конфигурация стенда, генератор/seed данных, размеры графов,
  p50/p95/p99 по группам, ошибки, таймауты и фактическая интенсивность.

## Требования

| ID | Требование | Проверка |
| --- | --- | --- |
| NFR-PERF-01 | Поиск и чтение карточки: p95 ≤ 1 с на P1 | Нагрузочный прогон, раздельная статистика двух операций |
| NFR-PERF-02 | Чтение дневника и сохранение питания/состава: p95 ≤ 2 с на P1 | Отдельные p95; сохранение включает commit |
| NFR-PERF-03 | Аналитика календарного месяца: p95 ≤ 3 с на P1 | Проверка результата против контрольных сумм и измерение полного ответа |
| NFR-PERF-04 | Доля неожиданных 5xx, таймаутов и пропущенных отправок < 1% на P1; неожиданные отказы валидным запросам также считаются сбоями | Нагрузочный отчёт; намеренно невалидные запросы проверяются отдельно |
| NFR-PERF-05 | Списки выдаются страницами, по умолчанию 30, максимум 100 элементов; порядок стабилен при неизменных данных | Граничные API-тесты, отсутствие повторов/пропусков при последовательном чтении |
| NFR-PERF-06 | Ни один расчёт или ожидание блокировки не занимает ресурсы бесконечно: серверный бюджет операции ≤ 10 с | Тест тяжёлого графа/занятой блокировки; отмена SQL и откат незавершённой операции; таймаут не возвращает частичный успех |
| NFR-PERF-07 | На устройстве 4 ГиБ RAM, 4 ядра, API 26+, release-сборка: первый интерактивный экран ≤ 3 с в 9 из 10 холодных запусков; индикатор запроса появляется ≤ 300 мс | Отдельный инструментальный прогон; сеть не задерживает показ оболочки/загрузки, характеристики устройства записываются |

Вне P1 корректность данных обязательна, но указанные времена не гарантируются.
При исчерпании бюджета показывается понятная ошибка, а не обрезанный состав или
неполная аналитика. Жёсткие продуктовые лимиты глубины, количества компонентов и
максимальных чисел не вводятся этим документом: их обоснование — задача проектирования
до реализации схемы/API. Ограничения должны быть явными, без скрытого усечения.

Рекурсивный SQL раскрывает пути, поэтому число продуктов само по себе недостаточно
для оценки нагрузки. Отдельный стресс-сценарий многократно общих подграфов обязателен.
Нельзя достигать целевого времени за счёт постоянного хранения КБЖУ или аналитики.
