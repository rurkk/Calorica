# Нефункциональные требования

Статус: проект требований второго этапа, подготовленный по поручению владельца.
Числовые цели выбраны для учебного MVP; это не результаты измерений и не обещание
производительности текущего Android-каркаса. Принятые ранее продуктовые решения сохранены.

## Разделы

- [Производительность и нагрузка](performance.md).
- [Надёжность, сохранность и эксплуатация](reliability.md).
- [Безопасность и изоляция данных](security.md).
- [Совместимость, удобство и доступность](usability-and-compatibility.md).
- [Порядок приёмки](../acceptance/README.md).

Каждое требование имеет идентификатор NFR и способ проверки. «Должно» обозначает
целевое поведение готового MVP, а не подтверждение реализации. Новые числовые значения
можно уточнить до утверждения ТЗ; после утверждения изменения фиксируются вместе
с причиной, влиянием на сроки и обновлённой проверкой.

## Границы

- Нагрузка и ресурсы для проверки задаются явно; не обещаем неограниченную глубину
  графа, число пользователей или доступность уровня промышленного кластера.
- Контроль доступа, запрет циклов и атомарность обязательны даже при одном Admin.
- Не добавляем защиту от перезаписи устаревшей формой, офлайн-запись или полный кэш.
- Точность и округление определены в [отдельной политике](../../architecture/numeric-precision.md).
- Целевое решение остаётся на одном VPS, без высокой доступности; потеря VPS покрывается
  резервной копией вне этого VPS и процедурой восстановления, не автоматическим failover.
