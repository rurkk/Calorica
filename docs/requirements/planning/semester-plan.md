# Объём и план на семестр

План реализации согласованного MVP задаёт последовательность работ,
зависимости и проверяемые результаты.

## Обязательный результат семестра

Работающее Android-приложение и сервер: email/пароль, профиль с необязательными
ориентирами, базовый/личный каталог, граф состава, два способа ввода и два режима
выхода, дневник, календарная аналитика, администрирование каталога, независимый
автоматический выпуск, развёртывание и проверка сохранности данных.

Всё перечисленное входит в исходный план, а не в факультативный список.
Промежуточная вертикаль «войти → выбрать продукт → записать еду → увидеть итог»
нужна для ранней интеграции, но не заменяет окончательный объём.

## План работ

| Направление | Результат | Зависимости и контрольная точка |
| --- | --- | --- |
| Каркас | Схема данных, OpenAPI, прототипы основных экранов, миграции, регистрация/сессии и тестовый стенд | Утверждённое ТЗ; определить числовые границы и протокол гонок удаления. Получен первый запрос Android → API |
| Каталог и дневник | Базовый/личный каталог, поиск, профиль, ввод и просмотр питания по датам | Роли и API готовы; сквозной сценарий для конечного продукта, проверка изоляции аккаунтов |
| Расчётный домен | Вложенные составы, ввод долями/граммами, выход на связях/общий, мягкое и каскадное удаление | Корректные миграции и контролируемые примеры; рекурсивный SQL проверен на общих ингредиентах и конкуренции |
| Аналитика и клиент | Полная аналитика, продуктовые и пищевые лейблы, UTC, точность, управление каталогом в Android | Проверки AC-01 — AC-20; функциональный объём закрыт, перечень дефектов составлен |
| Выпуск | Независимый автоматический выпуск Android/сервера, целевое развёртывание, бэкапы, NFR и регрессионные проверки | Ресурсы/домен/секреты доступны; протокол нагрузки и восстановления, исправления по результатам |
| Приёмка | Исправления, итоговая приёмка, демонстрация и оформление материалов | Блокирующие дефекты устранены; результаты обязательных проверок подтверждены |

CI и проверки ключевых инвариантов вводятся по мере реализации, а не только в конце.
Локальный/тестовый стенд нужен для первого сквозного сценария. Целевое развёртывание
и пилот позволяют выполнить эксплуатационные проверки, включая измерение
доступности по условиям нефункциональных требований.

## За пределами обязательного MVP

- Полноценный Android-кэш — отдельная задача после завершения MVP;
  офлайн-очередь также не добавляется автоматически.
- Google-вход, восстановление/смена пароля, штрихкоды, фото, AI-диетолог.
- Web/iOS-клиенты, Google Play, пользовательские лейблы приёмов пищи.
- Дополнительные единицы помимо г/мл, синонимы, полнотекстовый поиск, избранное,
  рекомендации, автоматические ориентиры, БЖУ-переключатель пищевых столбцов.
- Автоматический учёт потерь отдельных нутриентов при приготовлении.
- Микросервисы, кластер высокой доступности, разрешение конфликтов устаревших форм.

## Риски и управление объёмом

| Риск | Действие |
| --- | --- |
| Недостаток опыта серверного Kotlin/Spring | Ранняя сквозная вертикаль, обычный JDBC/SQL, без дополнительной модульной инфраструктуры |
| Взрыв числа путей в графе | Профиль P1, стресс-примеры и бюджет запроса; при проблеме сначала оптимизация, затем явное согласование границ |
| Ошибки выхода и округления | Контрольные примеры до интеграции экранов, отдельная проверка исходных/готовых долей |
| Общий VPS не имеет нужных ресурсов | Проверка доступных ресурсов до production; перенос Calorica на отдельный хост без изменения домена |
| Независимые релизы ломают старый клиент | Совместимые изменения API, поэтапные миграции, проверка предыдущего клиента/серверного отката |
| Интеграция выявляет дополнительные работы | Пересмотреть последовательность после сквозного сценария; менять согласованный объём только с разрешения владельца и изменением ТЗ |

После контрольного результата фиксируются готовые функции, дефекты и следующий приоритет.
Новые идеи попадают в отложенный список, а не незаметно расширяют MVP.
