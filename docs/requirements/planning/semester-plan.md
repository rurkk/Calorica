# Объём и план на семестр

Статус: предложенный план реализации согласованного MVP. Ниже 12 относительных недель
от старта реализации; календарные дедлайны курса не предоставлены. Это не переименование
или изменение пяти учебных этапов Notion. Даты привязываются к расписанию отдельно.

## Обязательный результат семестра

Работающее Android-приложение и сервер: email/пароль, профиль с необязательными
ориентирами, базовый/личный каталог, граф состава, два способа ввода и два режима
выхода, дневник, календарная аналитика, администрирование каталога, независимый
автоматический выпуск, развёртывание и проверка сохранности данных.

Всё перечисленное входит в исходный план, а не в факультативный список.
Промежуточная вертикаль «войти → выбрать продукт → записать еду → увидеть итог»
нужна для ранней интеграции, но не заменяет окончательный объём.

## План работ

| Недели | Результат | Зависимости и контрольная точка |
| --- | --- | --- |
| 1–2 | Схема данных, OpenAPI, прототипы основных экранов, миграции, регистрация/сессии и тестовый стенд | Утверждённое ТЗ; определить числовые границы и протокол гонок удаления. Получен первый запрос Android → API |
| 3–4 | Базовый/личный каталог, поиск, профиль, ввод и просмотр питания по датам | Роли и API готовы; сквозной сценарий для конечного продукта, проверка изоляции аккаунтов |
| 5–6 | Вложенные составы, ввод долями/граммами, выход на связях/общий, мягкое и каскадное удаление | Корректные миграции и контролируемые примеры; рекурсивный SQL проверен на общих ингредиентах и конкуренции |
| 7–8 | Полная аналитика, продуктовые и пищевые лейблы, UTC, точность, управление каталогом в Android | Проверки AC-01 — AC-20; функциональный объём закрыт, перечень дефектов составлен |
| 9–10 | Независимый автоматический выпуск Android/сервера, целевое развёртывание, бэкапы, NFR и регрессионные проверки | Ресурсы/домен/секреты доступны; протокол нагрузки и восстановления, исправления по результатам |
| 11–12 | Резерв на интеграцию и дефекты, итоговая приёмка, демонстрация и оформление материалов | Нельзя расходовать резерв на новые функции до устранения блокирующих дефектов |

CI и проверки ключевых инвариантов вводятся по мере реализации, а не только в конце.
Сборка production-ready инфраструктуры завершается на неделях 9–10; локальный/тестовый
стенд нужен раньше. Длительный пилот для измерения доступности желательно запустить
до финальной недели, иначе месячное измерение будет недоступно к демонстрации.

## За пределами обязательного MVP

- Полноценный Android-кэш — отдельная задача после завершения MVP, без обещания
  включить его в эти 12 недель; офлайн-очередь также не добавляется автоматически.
- Google-вход, восстановление/смена пароля, штрихкоды, фото, AI-диетолог.
- Web/iOS-клиенты, Google Play, пользовательские лейблы приёмов пищи.
- Дополнительные единицы помимо г/мл, синонимы, полнотекстовый поиск, избранное,
  рекомендации, автоматические ориентиры, БЖУ-переключатель пищевых столбцов.
- Автоматический учёт потерь отдельных нутриентов при приготовлении.
- Микросервисы, кластер высокой доступности, разрешение конфликтов устаревших форм.

## Риски и управление объёмом

| Риск | Действие |
| --- | --- |
| Недостаток опыта серверного Kotlin/Spring | Ранняя сквозная вертикаль, обычный JDBC/SQL, без дополнительной модульной инфраструктуры |
| Взрыв числа путей в графе | Профиль P1, стресс-примеры и бюджет запроса; при проблеме сначала оптимизация, затем явное согласование границ |
| Ошибки выхода и округления | Контрольные примеры до интеграции экранов, отдельная проверка исходных/готовых долей |
| Общий VPS не имеет нужных ресурсов | Проверка доступных ресурсов до production; перенос Calorica на отдельный хост без изменения домена |
| Независимые релизы ломают старый клиент | Совместимые изменения API, поэтапные миграции, проверка предыдущего клиента/серверного отката |
| Сроки не соответствуют доступности команды | Перепланировать после первых двух недель; исключать согласованные функции только с разрешения владельца и изменением ТЗ |

Раз в неделю фиксируются готовые результаты, отклонения и следующий приоритет.
Новые идеи попадают в отложенный список, а не незаметно расширяют MVP.
