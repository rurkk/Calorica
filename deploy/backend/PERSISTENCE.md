# T17: миграции, сохранность и совместимость возврата backend

Действующая доставка — [GitHub Actions → GHCR → Render](../render/README.md),
БД — Neon. Эти испытания выполняются только локально. Скрипт не принимает
`DB_URL`, имя существующего контейнера или параметры провайдера и не обращается
к общей БД. Обычный release не останавливает и не пересоздаёт PostgreSQL.

## Повторяемый прогон

Нужны JDK 21, Python 3.9+ и работающий Docker с `postgres:17.11-bookworm`.
Выполнять из корня репозитория. JAR кандидата собирается в отдельной рабочей
копии на зафиксированном SHA:

```sh
# JAVA_HOME должен указывать на JDK 21.
(cd backend && ./gradlew --no-daemon bootJar)
```

Предыдущий JAR извлекается из **точного выпущенного digest**, без запуска его
контейнера. Подставить проверенный digest и новый временный каталог:

```sh
release_image='ghcr.io/rurkk/calorica-backend@sha256:<64 hex digits>'
docker pull --platform linux/amd64 "$release_image"
docker image inspect "$release_image" \
  --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}'
artifact_dir=$(mktemp -d /tmp/calorica-t17-artifacts-XXXXXXXX)
extract_id=$(docker create --platform linux/amd64 "$release_image")
docker cp "$extract_id:/app/app.jar" "$artifact_dir/previous.jar"
docker rm "$extract_id"
```

Сверить label с SHA выпущенного backend, а digest — с Render Events и результатом
GHCR release. Сохранить эту связь в отчёте. `--previous-source` и `--current-source`
— записываемые сведения оператора, а не автоматическое доказательство происхождения;
скрипт дополнительно сохраняет SHA-256 обоих JAR.

```sh
python3 deploy/backend/persistence_drill.py \
  --previous-jar "$artifact_dir/previous.jar" \
  --current-jar backend/build/libs/calorica-backend.jar \
  --previous-source '<released source SHA and image digest>' \
  --current-source "$(git rev-parse HEAD)" \
  --output /tmp/calorica-t17-unique-run
```

По умолчанию выполняется `--phase full`: требуются T11, T13, T14 и T15.
Для предварительной проверки до их интеграции явно передать `--phase preliminary`;
этот режим записывается в отчёт и не является полной SA-17.

Каталог `--output` должен быть новым. Он создаётся с приватными правами; `report.json`
содержит только версии, migration checksums, количества таблиц и результаты. JVM-логи
остаются локальными: перед передачей проверять их содержимое. Пароли, access/refresh
токены и данные аккаунта не печатаются в отчёте. Не помещать сырые логи в Git.

Скрипт создаёт один контейнер со случайным именем `calorica-t17-*`, меткой владения,
свободным loopback-портом, закреплённым на весь прогон, и собственным томом. В нём две отдельные БД: `fresh`
и `upgrade`. Подпроцесс JVM получает только заданные тестовые DB/auth настройки,
не наследует пользовательские `DB_*`, `SPRING_*` и `JAVA_TOOL_OPTIONS`. При завершении
удаляются только этот контейнер и его анонимный том, после проверки метки владения.
Не использовать `docker prune`, `down -v` или остановку общих сервисов.

## Что проверяется

1. SQL всех ранее выпущенных changesets побайтно совпадает с кандидатом.
2. Кандидат создаёт всю текущую production-схему с нуля.
3. Старый backend создаёт предыдущую схему, подтверждает регистрацию, профиль
   и личные продукты через HTTP. Кандидат обновляет эту БД; старые значения,
   checksums и порядок применённых changesets сохраняются, fresh/upgrade совпадают.
4. Через API создаются состав с выходами ингредиентов, дневник с несколькими
   пищевыми лейблами и конвертация мл → г. В полном режиме также создаются
   GRAMS/outputGrams, продуктовые лейблы на листьях и родителе, мягкий каскад
   с сохранённой историей; календарная аналитика входит в повторяемый снимок.
   КБЖУ берутся из серверного расчёта;
   контрольные числа — из SA-07/SA-12, второй расчётный движок не создаётся.
5. JVM останавливается, затем запускается новый процесс. Проверяются полные HTTP
   ответы, fingerprint всех строк каждой предметной таблицы и история Liquibase.
6. PostgreSQL останавливается при работающей JVM. Readiness становится `503 DOWN`,
   liveness остаётся `200 UP`. После старта проверяется изменение времени запуска
   postmaster, восстановление readiness и тех же данных/ссылок/расчётов.
7. Правка ингредиента меняет расчёт существующего дневника. Неудачная тестовая
   миграция (создание таблицы и деление на ноль в одной транзакции) прерывает старт,
   не оставляет таблицу или запись changeset и не меняет подтверждённые данные.
8. Старый backend запускается **без отката схемы**. Проверяются аккаунт, продукт,
   состав и дневник. Неготовность API или неверный расчёт означают несовместимость,
   даже если readiness вернул `UP`. Затем кандидат запускается снова, и данные
   перепроверяются. Проверяется сохранённая refresh-сессия старой версии.

Успешные промежуточные пункты остаются в JSON даже при провале последующего.
Любая несовместимость возвращает ненулевой код. Такой отчёт нельзя использовать
как разрешение на production rollback или как закрытие T17.

## Как принимать решение о возврате образа

До выпуска сохранить digest текущего backend, его OCI revision, список применённых
миграций и digest кандидата. На изолированной БД проверить **эту пару артефактов**
с актуальной схемой и данными всех предметных областей. Только функционально
совместимый образ допустим для ручного workflow `Render deploy existing image`.
Доставку выполняет ответственный после согласия владельца на конкретный объём.

После failed deploy проверить Render Events, фактический digest и публичный
readiness. Не считать `Live` доказательством готовности. Не повторять POST deploy
вслепую после потери ответа API. Render-скрипт не сохраняет новый Image URL до
успешных Live и readiness; это не обещание автоматического возврата работающего
процесса. При несовместимости старого backend восстановить работоспособность
исправленным совместимым кандидатом; БД и применённые SQL не откатывать.

Проверенный предыдущий релиз от 1 ноября 2026:
`fb97cef7ade7015450328fd3dc2902792648df0e`,
`ghcr.io/rurkk/calorica-backend@sha256:52969c9ad166bf79e167ce0645a29d39411cc45083ec29be53f8cbd56742a0b0`.
Он содержит только `001/010/020/025` и не реализует составы/дневник. Его нельзя
считать полноценной rollback-базой после появления этих данных. Старый артефакт
не изменяется; для будущего возврата нужен отдельно выпущенный и функционально
проверенный совместимый backend. История повторяемого прогона фиксируется отдельно
для каждого candidate SHA; предварительная схема без T13 не подтверждает всю SA-17.

## Автоматические проверки инструмента и доставки

```sh
python3 -m unittest discover -s deploy/backend -p 'test_*.py'
python3 -m unittest discover -s scripts/ci -p 'test_render_deploy.py'
```

Первая команда проверяет запрет изменения применённого SQL и защиту cleanup от
чужого контейнера. Вторая — существенные отказные ветви действующей доставки:
неверный digest/сервис, отказ/таймаут Render, несовпавший live digest, неготовый
readiness и отказ сохранения Image URL. Эти тесты не делают сетевых запросов.
Проверки `deploy.sh` относятся к историческому VPS/локальному Compose; они не
доказывают rollback в Render.

Внешние/ежедневные backup и restore-drill исключены из обязательной семестровой
приёмки решением T00 от 1 ноября 2026. Эта проверка не доказывает восстановление
после потери диска, RPO/RTO или доступность провайдеров. Подписанный APK,
физическое устройство, независимые GitHub releases и выпущенный backend проверяются
отдельно в T01/T16/T18. T17 остаётся открытой до финальной схемы T11–T15,
повторения другим участником и согласованной интеграции/доставки.

## Предварительный результат 4 ноября 2026

На кандидате `e7ce78b` (7 changesets, до T11–T15) выполнен режим `preliminary`
против точного JAR предыдущего image выше. Среда: Corretto 21.0.12.1, PostgreSQL
17.11-bookworm ARM64, Docker 24.0.5, Python 3.13.0. Пройдены fresh/upgrade 4→7,
сохранение исходных checksums, реальные перезапуски JVM/PostgreSQL, health при
отказе БД, неудачная транзакционная миграция, сохранность после возврата кандидата
и сохранённая refresh-сессия. Fingerprint всех строк 11 предметных таблиц и
HTTP-ответы после каждого перезапуска совпали.

**Откат на опубликованный backend несовместим:** readiness поднимается, но чтение
нового состава без ручных КБЖУ возвращает HTTP 500. Прогон корректно завершился
с кодом 1 и общим `FAIL`; данные не изменились, кандидат снова успешно их прочитал.
Это доказательство отказа от такого rollback, а не успешная приёмка T17. Полный
режим с финальной схемой T13 и сценариями T11–T15 ещё требуется повторить.
